## 📚 核心内容

### 为什么需要多进程

Python 的 GIL（全局解释器锁）导致同一时刻只有一个线程能执行 Python 字节码——**CPU 密集型任务用多线程无法充分利用多核**。多进程绕过 GIL，每个进程有独立的 Python 解释器和 GIL，真正实现并行：

```python
import time
import threading
import multiprocessing

def cpu_bound(n):
    total = 0
    for i in range(n):
        total += i
    return total

N = 50_000_000

# 多线程 — 受 GIL 限制
start = time.time()
threads = [threading.Thread(target=cpu_bound, args=(N,)) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(f'多线程：{time.time() - start:.2f}s')   # 接近单线程耗时

# 多进程 — 绕过 GIL，真正并行
start = time.time()
procs = [multiprocessing.Process(target=cpu_bound, args=(N,)) for _ in range(4)]
for p in procs: p.start()
for p in procs: p.join()
print(f'多进程：{time.time() - start:.2f}s')   # 约为多线程的 1/4
```

| 场景 | 选多线程 | 选多进程 |
|------|---------|---------|
| IO 密集型（网络请求、文件读写） | ✅ | 也可以，但进程开销更大 |
| CPU 密集型（计算、图像处理） | ❌ 受 GIL 限制 | ✅ 真正并行 |

**为什么多进程能绕过 GIL？** GIL 是**解释器级别**的互斥锁——每个 CPython 解释器实例内部有一个 GIL，不是操作系统级别的全局锁。`multiprocessing` 每创建一个子进程，底层做了三件事：

1. `fork()` 或 `spawn()` 创建一个全新的 OS 进程
2. 新进程中启动一个**全新的 CPython 解释器**
3. 这个新解释器自带一个**全新的、独立的 GIL**

![[90-Storage/98-Asset-资源/InfoGraphic/PY027-进程/GIL解释器级别互斥锁-信息图-v1.png]]

> 一个程序 `multiprocessing` 跑多进程 = 多个 OS 进程 → 多个 CPython 解释器 → 多个互相独立的 GIL → 各跑各的。这也是多进程开销大的原因：每个子进程都需要独立的内存空间和全新建解释器。

### 创建进程

`Process()` 构造函数接受以下参数：

| 参数 | 说明 |
|------|------|
| `target` | 子进程执行的函数 |
| `args` | 元组，传给 `target` 的位置参数 |
| `kwargs` | 字典，传给 `target` 的关键字参数 |
| `name` | 自定义进程名（默认 `Process-N`） |
| `daemon` | 布尔值，是否守护进程，必须在 `start()` 前设置 |

`start()` 启动子进程后立即返回——主进程和子进程并发执行（非阻塞）。`join()` 让主进程停在原地，等待子进程结束后再继续：

```python
from multiprocessing import Process
import os

def worker(name, num):
    print(f'子进程 PID={os.getpid()}，参数：{name}, {num}')

if __name__ == '__main__':
    p = Process(target=worker, args=('Alice', 42))
    p.start()               # 启动子进程（非阻塞，主进程继续往下走）
    p.join()                # 等待子进程结束
    print('子进程已结束')
```

**获取进程信息**：

```python
import os
import multiprocessing

os.getpid()                              # 当前进程的 PID（操作系统分配的唯一编号）
os.getppid()                             # 父进程的 PID（parent process ID）

p = Process(target=worker)
p.pid                                    # 子进程启动后才有值，启动前为 None
p.name                                   # 进程名称，如 'Process-1'

multiprocessing.current_process().name   # → 'MainProcess' 或其他名称
multiprocessing.current_process().pid    # 等价于 os.getpid()
```

> `os.getpid()` 和 `os.getppid()` 也适用于线程——线程和进程共享同一个 PID。`p.pid` 在 `start()` 之后才被赋值。

> ==`if __name__ == '__main__'` 在多进程中不是可选的——Windows 和 macOS 的 `spawn` 模式下，缺少这行代码会导致子进程递归创建，直接报错或死循环。==

**`join()` 和 `terminate()`**：

```python
p = Process(target=long_task)
p.start()

p.join(timeout=5)       # 最多等 5 秒，超时继续执行后续代码
if p.is_alive():
    p.terminate()        # 强制终止子进程（发送 SIGTERM）
    p.join()             # 等待终止完成
```

| 方法 | 作用 | 阻塞？ |
|------|------|--------|
| `start()` | 启动子进程 | 否 |
| `join()` | 等待子进程结束 | 是（可设 timeout） |
| `terminate()` | 强制终止子进程 | 否 |
| `is_alive()` | 判断子进程是否还在运行 | 否 |

### 继承式创建（子类化 Process）

对于复杂任务，继承 `Process` 重写 `run()` 更清晰：

```python
class DownloadProcess(Process):
    def __init__(self, url, save_path):
        super().__init__()
        self.url = url
        self.save_path = save_path

    def run(self):
        print(f'下载 {self.url} → {self.save_path}')
        # 实际下载逻辑

if __name__ == '__main__':
    p = DownloadProcess('https://example.com/file.zip', './file.zip')
    p.start()
    p.join()
```

### 父进程与子进程

#### 父子关系

当调用 `p.start()` 时，操作系统创建一个全新的进程：

```python
import os
from multiprocessing import Process

def child_task():
    print(f'子进程 PID={os.getpid()}，父进程 PPID={os.getppid()}')

if __name__ == '__main__':
    print(f'主进程 PID={os.getpid()}')
    p = Process(target=child_task)
    p.start()
    p.join()
# 主进程 PID=12345
# 子进程 PID=12346，父进程 PPID=12345
```

- **父进程（Parent）**：调用 `Process(target=…).start()` 的那个进程，负责创建和管理子进程
- **子进程（Child）**：被 `start()` 创建出来的新进程，执行 `target` 指定的函数
- `os.getppid()` 在子进程中返回的值 **等于父进程的 PID**

> 在命令行中可以用 `ps -ef | grep python` 查看父子进程的层级关系。

#### 内存隔离

子进程创建时，**不共享父进程的内存空间**——子进程会获得父进程内存的一份**独立拷贝**（Copy-on-Write 机制）。这意味着：

```python
data = [0]  # 父进程中的变量

def worker():
    data[0] = 100  # 修改的是子进程自己的副本
    print(f'子进程 data={data}')

if __name__ == '__main__':
    p = Process(target=worker)
    p.start()
    p.join()
    print(f'父进程 data={data}')  # 仍然是 [0]，不受子进程影响
# 子进程 data=[100]
# 父进程 data=[0]
```

因此进程间共享数据**必须通过专门的 IPC 机制**（Queue、Pipe、共享内存），不能像线程那样直接读写全局变量。

#### 进程的关闭与回收

子进程结束后**不会自动消失**——它变成了僵尸进程（zombie），等待父进程"收尸"。不回收的后果：

| 场景 | 不处理会怎样 |
|------|------------|
| `Process` 不 `join()` | 子进程变成僵尸进程，占用进程表条目；进程数量多了会导致系统无法创建新进程 |
| `Pool` 不 `close()`/`join()` | 工作进程持续存在，主进程退出后变成孤儿进程 |
| 主进程先于子进程退出 | 子进程变成孤儿进程，由 init（PID=1）接管回收 |

**`Process`：两种回收方式**

```python
from multiprocessing import Process
import time

def worker():
    time.sleep(3)

# 方式 1：join() — 等子进程结束，回收资源
p = Process(target=worker)
p.start()
# ... 主进程做别的事情
p.join()          # 阻塞等待子进程结束，回收 OS 资源
print('子进程已回收')

# 方式 2：join(timeout) + terminate() — 超时强制终止
p = Process(target=worker)
p.start()
p.join(timeout=1)  # 只等 1 秒
if p.is_alive():
    p.terminate()   # 强制杀死子进程
    p.join()        # 回收资源（terminate 后必须再 join）
```

> `terminate()` 发送 `SIGTERM` 信号强制终止，子进程没有机会做清理（无法执行 `finally` 块或 `atexit` 回调）。只有确定子进程卡死/不需要优雅退出时才用它。

**`Pool`：必须 close + join**

```python
from multiprocessing import Pool

# 推荐：with 语句自动处理
with Pool(processes=4) as pool:
    results = pool.map(square, [1, 2, 3, 4, 5])
# ← 退出 with 时自动 close() + join()，工作进程全部回收

# 不用 with 时要手动关闭
pool = Pool(4)
try:
    results = pool.map(square, [1, 2, 3, 4, 5])
finally:
    pool.close()   # 不再接受新任务
    pool.join()    # 等待所有工作进程退出并回收
```

| 方法 | 作用 |
|------|------|
| `close()` | 关闭池，不再接受新任务（已提交的任务继续执行） |
| `join()` | 等待所有工作进程退出 |
| `terminate()` | 立即杀死所有工作进程（不等待任务完成） |

> `close()` 和 `join()` 必须按顺序调用，并且 `join()` 必须在 `close()` 之后——否则会报错。

**`ProcessPoolExecutor`：用 with 最省心**

```python
from concurrent.futures import ProcessPoolExecutor

# with 退出时自动调用 shutdown(wait=True)，等于 close + join
with ProcessPoolExecutor(max_workers=4) as executor:
    results = executor.map(square, [1, 2, 3, 4, 5])
# ← 工作进程全部回收
```

**daemon（守护进程）：自动跟随主进程退出**

```python
p = Process(target=worker, daemon=True)
p.start()
# 主进程退出时，daemon 子进程被自动终止，不需要 join
```

> `daemon=True` 的进程不能创建自己的子进程，且被终止时没有清理机会。适合后台心跳、监控这类"主进程死了就没意义了"的任务。

**一图总结各方式的关闭要求**：

| 方式 | 需要关闭？ | 推荐写法 |
|------|----------|---------|
| `Process` | 需要 `join()` 回收 | `p.join()` |
| `Process(daemon=True)` | 不需要，随主进程自动退出 | 无需额外操作 |
| `Pool` | 必须 `close()` + `join()` | `with Pool() as pool:` |
| `ProcessPoolExecutor` | 必须 `shutdown()` | `with ProcessPoolExecutor() as executor:` |

### fork vs spawn

子进程的创建方式取决于操作系统的**启动方法（start method）**：

|               | fork               | spawn                                   |
| ------------- | ------------------ | --------------------------------------- |
| **默认平台**      | Linux              | **macOS**、Windows                       |
| **原理**        | 直接复制父进程的整个内存空间给子进程 | 启动一个**全新的空白 Python 解释器**，重新 import 当前模块 |
| **需要重新导入模块？** | 不需要，内存已复制          | **需要**——子进程必须能 `import` 到目标函数           |
| **速度**        | 快（写时复制）            | 慢（启动新解释器 + import 开销）                   |
| **安全性**       | 子进程可能继承父进程的不安全状态   | 子进程是干净的，更安全                             |

**`spawn` 下发生了什么**：

```
p.start()
  → 1. 启动一个全新的 Python 解释器
  → 2. 子进程 import 当前模块（你的 .py 文件）
  → 3. pickle 反序列化出 target 函数来执行
  → 4. 子进程执行 target(*args)
```

**为什么 `import` 而不是 `python bad.py`？** spawn 子进程的启动命令不是 `python bad.py`，而是一段内置引导代码，内部用 `importlib.import_module('bad')` 导入你的模块。**这是刻意设计的**——如果运行的是 `python bad.py`，那 `__name__` 永远是 `'__main__'`，无论怎么加保护都没用，必然无限递归。只有用 `import`，子进程中的 `__name__` 才会是 `'bad'`（模块名），从而让 `if __name__ == '__main__'` 有了区分的可能。

**不加保护会怎样？** 看一个具体例子：

```python
# bad.py — 没有 if __name__ == '__main__' 保护
from multiprocessing import Process

def worker():
    print('子进程工作中')

p = Process(target=worker)  # 顶层代码，import 时也会执行
p.start()
p.join()
```

运行 `python bad.py` 后发生了什么：

```
第 1 层：你在终端执行 python bad.py
  → __name__ 是 '__main__'，从头执行代码
  → 执行到 p = Process(target=worker)
  → p.start() 触发 spawn，启动一个新解释器

第 2 层（子进程）：新解释器 import bad
  → __name__ 是 'bad'，但 import 仍然执行顶层代码！
  → 执行到 p = Process(target=worker)  ← 又来了
  → p.start() 再次 spawn → 第 3 层 → 第 4 层 → 无限递归
```

加上保护之后：

```python
# good.py
from multiprocessing import Process

def worker():
    print('子进程工作中')

if __name__ == '__main__':         # 直接运行时才进入
    p = Process(target=worker)
    p.start()
    p.join()
```

```
python good.py
  → __name__ 是 '__main__'，进入 if 块，创建子进程 ✅

子进程 import good
  → __name__ 是 'good'，不等于 '__main__'
  → if 块被跳过，只定义了 worker 函数，不创建进程 ✅
  → 子进程正常执行 worker，然后退出
```

`if __name__ == '__main__'` 的作用就是一句话：**告诉 Python "这些代码只在直接运行脚本时执行，被 import 时跳过"**。spawn 用 `import` 加载你的模块，所以必须有这条防线来挡住子进程。

#### 为什么交互式环境（Jupyter/IPython）不能用 multiprocessing

在 Jupyter 中直接定义函数并用 `Process(target=…)` 会报错：

```
AttributeError: Can't get attribute 'process_func' on <module '__main__' ...>
```

原因在于 **`spawn` 的 import 机制**：

1. pickle 序列化 `process_func` 时，记录它的"地址"是 `__main__.process_func`
2. 子进程启动后执行 `import __main__` 来找回这个函数
3. 但 Jupyter 的 `__main__` **不是磁盘上的 `.py` 文件**——它是 IPython kernel 的运行时环境
4. 子进程 import 到的 `__main__` 是一个空的 `BuiltinImporter` 对象，**没有你定义的函数**
5. pickle 反序列化失败 → `AttributeError`

**解决方案**：把 `target` 函数放到独立的 `.py` 文件里 import：

```python
# worker.py
def process_func():
    print("Hello from child")

# Jupyter cell
from worker import process_func
from multiprocessing import Process

p = Process(target=process_func)
p.start()  # ✅ 子进程 import worker 可以找到 process_func
p.join()
```

> 也可以用 `multiprocessing.set_start_method('fork')` 强制使用 fork（仅 macOS，且 Python 3.8+ 已标记为不安全），但这只是绕过问题——最可靠的方式永远是**把 target 函数放在独立的 `.py` 模块中**。

### 进程池：Pool

逐个创建 `Process` 在任务数多时开销大。`Pool` 预先创建固定数量的进程，任务队列式分配：

```python
from multiprocessing import Pool

def square(x):
    return x * x

if __name__ == '__main__':
    with Pool(processes=4) as pool:      # 4 个常驻工作进程
        # map — 分发任务，按顺序返回结果
        results = pool.map(square, [1, 2, 3, 4, 5])
        print(results)  # [1, 4, 9, 16, 25]

        # apply_async — 异步提交单个任务
        async_result = pool.apply_async(square, (10,))
        print(async_result.get())  # 100（阻塞直到结果就绪）
```

**Pool 常用方法**：

| 方法 | 行为 | 适用场景 |
|------|------|----------|
| `map(func, iterable)` | 分发，阻塞等全部完成，按顺序返回 | 批量处理，顺序有要求 |
| `map_async(func, iterable)` | 分发后立即返回 `AsyncResult` | 需要非阻塞提交 |
| `apply(func, args)` | 同步执行单个，阻塞等结果 | 单任务 |
| `apply_async(func, args)` | 异步执行单个，返回 `AsyncResult` | 带回调的单任务 |
| `imap(func, iterable)` | 惰性迭代器，有结果就返回 | 结果逐个处理，节省内存 |
| `close()` | 关闭池，不再接受新任务 | 配合 `join()` |
| `join()` | 等待所有工作进程退出 | 必须在 `close()` 之后 |

**回调函数**——任务完成时自动触发：

```python
def on_done(result):
    print(f'任务完成，结果：{result}')

if __name__ == '__main__':
    with Pool(4) as pool:
        pool.apply_async(square, (5,), callback=on_done)
```

> 回调函数在**主进程**中执行（不是工作进程），可以安全地操作主进程的数据。

### concurrent.futures.ProcessPoolExecutor

Python 3.2+ 引入的高级接口，与 `ThreadPoolExecutor` 统一 API：

```python
from concurrent.futures import ProcessPoolExecutor, as_completed

def task(n):
    return n * n

if __name__ == '__main__':
    with ProcessPoolExecutor(max_workers=4) as executor:
        # submit — 提交单个任务，返回 Future
        future = executor.submit(task, 10)
        print(future.result())  # 100

        # map — 批量提交，保持顺序
        for result in executor.map(task, [1, 2, 3, 4]):
            print(result)  # 1 4 9 16

        # as_completed — 哪个先完成就处理哪个（不保证顺序）
        futures = [executor.submit(task, i) for i in [10, 5, 8]]
        for f in as_completed(futures):
            print(f.result())  # 先完成先输出
```

**Pool vs ProcessPoolExecutor**：

| | `multiprocessing.Pool` | `ProcessPoolExecutor` |
|------|-----|------|
| 所属模块 | `multiprocessing` | `concurrent.futures` |
| 回调支持 | `callback` 参数 | `add_done_callback()` |
| 异常处理 | 子进程异常会静默 | `Future.result()` 会 re-raise |
| 取消任务 | 不支持 | `Future.cancel()` |
| 与线程池 API 统一 | ❌ | ✅ |

> 新项目优先选 `ProcessPoolExecutor`——API 更现代，和线程池接口统一，异常处理更直观。需要 `imap` 或更细粒度的任务队列控制时用 `Pool`。

### 进程间通信（IPC）

进程间内存不共享，每个进程有自己的地址空间。想让它们协作，必须通过操作系统提供的 IPC（Inter-Process Communication）机制：

![[90-Storage/98-Asset-资源/InfoGraphic/PY027-进程/IPC概览-信息图-v1.png]]

Python `multiprocessing` 提供了三种 IPC 方式：**Queue**（队列）、**Pipe**（管道）、**共享内存**（Value/Array）。

---

#### Queue — 多生产者 / 多消费者

##### 实现原理

Queue 的底层不是一个简单的列表——它由三部分组成：

1. **Pipe（管道）**：实际的数据传输通道，负责将字节流从一端送到另一端
2. **Lock（互斥锁）**：保证同一时刻只有一个线程在读写管道，防止字节流交叠
3. **Feeder Thread（后台 feeder 线程）**：`put()` 调用后，由这个线程负责将对象序列化并写入管道，实现异步投递

**为什么 Lock 管的是「线程」而不是「进程」？** 管道（Pipe）本身不是线程安全的——两个线程同时向同一根管道写，各自的字节流会交错在一起，反序列化时必然出错。而一个进程内部，可能同时有多个线程往同一个 Queue `put()`，再加上 Queue 自带的 feeder 后台线程也要写这根管道，所以「同一根管道的并发写入」是真实存在的。Lock 的作用就是**串行化写操作**：同一时刻只让一个线程写，写完一个对象再写下一个。

进程之间的安全靠的是**管道端点隔离**：Queue 底层的管道是单向的，进程 A 只持有写端，进程 B 只持有读端，各写各的端点，天然不会抢同一根管道。所以 Lock 不需要管进程之间，只管进程内部的线程。

![[90-Storage/98-Asset-资源/InfoGraphic/PY027-进程/Queue内部结构-信息图-v1.png]]

当调用 `q.put(obj)` 时：
1. `obj` 被 **pickle 序列化**为字节流
2. 后台 feeder 线程将字节流写入底层 Pipe
3. 管道另一端的 `q.get()` 读取字节流并 **pickle 反序列化**还原对象

> **关键**：Queue 传递的是对象的**副本**，不是引用。进程 A `put` 一个列表，进程 B `get` 到的是一个全新的列表对象，修改互不影响。这正是进程隔离的体现。

##### 基本用法

```python
from multiprocessing import Process, Queue

def producer(q):
    for i in range(5):
        q.put(f'数据_{i}')    # put：放数据到队列（可能阻塞，见下文）
    q.put(None)               # 哨兵值（sentinel）：通知消费者"没数据了"

def consumer(q):
    while True:
        item = q.get()         # get：从队列取数据（队列空时会阻塞等待）
        if item is None:       # 识别哨兵，退出循环
            break
        print(f'消费：{item}')

if __name__ == '__main__':
    q = Queue()
    Process(target=producer, args=(q,)).start()
    Process(target=consumer, args=(q,)).start()
```

##### put/get 的阻塞行为

| 操作 | 队列状态 | 默认行为 | `timeout` 参数 |
|------|----------|----------|---------------|
| `put(obj)` | 队列满 | **阻塞等待**，直到有空位 | `put(obj, timeout=3)` → 3 秒后抛 `queue.Full` |
| `get()` | 队列空 | **阻塞等待**，直到有新数据 | `get(timeout=3)` → 3 秒后抛 `queue.Empty` |

```python
q = Queue(maxsize=2)      # 最大容量 2
q.put('A')
q.put('B')
# q.put('C')              # 默认阻塞！队列满了，等消费者取走一个
q.put('C', timeout=1)     # 1 秒后抛 queue.Full 异常

# 非阻塞版本
q.put_nowait('C')         # 队列满立刻抛异常，等价于 put(obj, block=False)
q.get_nowait()            # 队列空立刻抛异常
```

##### 为什么需要哨兵（sentinel）？

消费者在 `while True` 中循环 `get()`，如果生产者不发了，消费者会**永远阻塞**在 `get()` 上——它不知道"没数据了"。哨兵就是那个"不发了"的信号。

```python
# 多个消费者时，每个消费者都要收到哨兵
NUM_WORKERS = 3
q = Queue()

# 启动 3 个 worker
for i in range(NUM_WORKERS):
    Process(target=worker, args=(q,)).start()

# 生产数据...
for url in urls:
    q.put(url)

# 每个 worker 发一个哨兵
for _ in range(NUM_WORKERS):
    q.put(None)
```

> 也可以用 `multiprocessing.JoinableQueue` + `task_done()` / `join()` 模式替代哨兵，适合已知任务总量的场景。

#### Pipe — 点对点双工通道

##### 实现原理

![[90-Storage/98-Asset-资源/InfoGraphic/PY027-进程/Pipe点对点通信-信息图-v1.png]]

`Pipe()` 返回一对 **Connection** 对象，底层是操作系统提供的匿名管道。数据从一端 `send()` 进去，另一端 `recv()` 出来，**先进先出（FIFO）**。

> 和 Queue 不同，Pipe **没有后台 feeder 线程**——数据直接走 OS 管道，少了线程中转的开销，但也失去了多消费者支持。

##### 基本用法

```python
from multiprocessing import Pipe, Process

def sender(conn):
    conn.send('你好')         # 发送一个字符串
    conn.send([1, 2, 3])     # 发送一个列表（会被 pickle 序列化）
    conn.close()             # 关闭连接，通知对方"我发完了"

def receiver(conn):
    print(conn.recv())       # '你好'
    print(conn.recv())       # [1, 2, 3]
    # conn.recv()            # 再 recv 会抛 EOFError，因为 sender 已 close
    conn.close()

if __name__ == '__main__':
    parent_conn, child_conn = Pipe()   # Pipe() 默认 duplex=True（双向）
    Process(target=sender, args=(child_conn,)).start()
    Process(target=receiver, args=(child_conn,)).start()
```

##### 双工 vs 半双工

```python
# duplex=True（默认）：两端都可以 send 和 recv
parent_conn, child_conn = Pipe(duplex=True)
parent_conn.send('主→子')      # 父发子收
reply = parent_conn.recv()     # 父收子发

# duplex=False：只读端 + 只写端（单向管道）
reader, writer = Pipe(duplex=False)
writer.send('只能写')          # reader 端不能 send
data = reader.recv()           # writer 端不能 recv
```

> **注意**：即使是 `duplex=True`，**同一端不能两个线程同时读写**——`send()` 和 `recv()` 自身不是线程安全的。

##### 如何知道对方发完了？

```python
def sender(conn):
    conn.send('msg1')
    conn.send('msg2')
    conn.close()          # ← 关键：关闭连接

def receiver(conn):
    while True:
        try:
            msg = conn.recv()
            print(msg)
        except EOFError:  # 对方 close 了，管道里也没数据了
            break
    conn.close()
```

`close()` 的作用不是销毁对象，而是**告诉对方"我不再写了"**。接收方继续 `recv()` 直到管道排空后收到 `EOFError`。

##### Pipe 的典型场景：双向 RPC

```python
def worker(conn):
    while True:
        try:
            cmd, arg = conn.recv()
        except EOFError:
            break
        if cmd == 'square':
            conn.send(arg * arg)     # 处理后回复结果
        elif cmd == 'exit':
            break

if __name__ == '__main__':
    parent_conn, child_conn = Pipe()
    p = Process(target=worker, args=(child_conn,))
    p.start()

    parent_conn.send(('square', 5))   # 请求
    result = parent_conn.recv()        # 等待回复
    print(result)  # 25

    parent_conn.send(('exit', None))
    parent_conn.close()
    p.join()
```

##### Queue vs Pipe

| | Queue | Pipe |
|------|-------|------|
| 通信模型 | 多生产者 / 多消费者 | 点对点（两个端点） |
| 底层实现 | Pipe + Lock + Feeder Thread | 直接 OS 管道 |
| 线程/进程安全 | ✅ | ✅（但同一端不能同时读写） |
| 数据流向 | 先进先出 | 先进先出（双向） |
| 适用场景 | 任务分发、工作队列 | 两进程直连、RPC |
| 额外开销 | 有（序列化 + 锁 + 后台线程） | 较小 |

#### 共享内存：Value / Array

Queue 和 Pipe 都走"复制 → 传输 → 还原"路线——大数据量时序列化开销很大。共享内存直接让多个进程**读写同一块物理内存**，没有传输开销。

##### 实现原理

![[90-Storage/98-Asset-资源/InfoGraphic/PY027-进程/共享内存mmap原理-信息图-v1.png]]

底层通过 `mmap`（内存映射）实现：操作系统将同一块物理内存分别映射到两个进程的虚拟地址空间中。进程 A 写一个值，进程 B 立刻能看到——**没有序列化，没有复制**。

##### 基本用法

```python
from multiprocessing import Process, Value, Array

def increment(shared_val, shared_arr):
    with shared_val.get_lock():        # 加锁保护：读-改-写必须原子
        shared_val.value += 1
    shared_arr[0] += 10                # Array 元素操作也需要小心

if __name__ == '__main__':
    val = Value('i', 0)                # 'i' = C signed int，初始值 0
    arr = Array('i', [0, 0, 0])        # 长度为 3 的 int 数组

    procs = [Process(target=increment, args=(val, arr)) for _ in range(4)]
    for p in procs: p.start()
    for p in procs: p.join()

    print(val.value)  # 4
    print(arr[:])     # [40, 0, 0]
```

##### typecode（类型代码）

共享内存需要知道**C 语言层面的数据类型和大小**，所以用单字符 typecode 指定：

| typecode | C 类型 | Python 类型 | 字节数 |
|----------|--------|-------------|--------|
| `'i'` | signed int | int | 4 |
| `'l'` | signed long | int | 4 或 8（平台相关） |
| `'f'` | float | float | 4 |
| `'d'` | double | float | 8 |
| `'c'` | char | bytes(1) | 1 |
| `'b'` | signed char | int | 1 |

##### 为什么需要 Lock？

`shared_val.value += 1` 看起来是一步，实际是三步：

```
1. 读取当前值 (LOAD)
2. 加 1        (ADD)
3. 写回        (STORE)
```

如果两个进程同时执行，可能发生：

```
进程 A: LOAD  val=0    →    ADD 1    →    STORE val=1
进程 B: LOAD  val=0*   →    ADD 1    →    STORE val=1
        ↑ B 在 A 写回前就读了旧值，两次加 1 结果却是 1
```

`with shared_val.get_lock()` 保证同一时刻只有一个进程执行 LOAD→ADD→STORE 这个完整序列。不加锁时，两个进程各加 100000 次，最终值大概率小于 200000——这就是**竞态条件（race condition）**。

##### 共享内存 vs Queue/Pipe

| | Queue / Pipe | Value / Array |
|------|-------------|---------------|
| 数据传递方式 | pickle 序列化 → 传输 → 反序列化 | 直接读写同一块内存 |
| 速度 | 慢（有复制开销） | 快（零复制） |
| 同步 | 天然同步（get 取走一个少一个） | 需要手动加 Lock |
| 适用场景 | 传递任务、传递结果 | 共享计数器、共享大数组 |
| 可传递类型 | 任意可 pickle 对象 | 仅 C 基本类型 |

> **原则**：传递任务和结果用 Queue/Pipe；多个进程需要读写**同一份**数据（尤其是大数组）时用共享内存。

#### Manager：共享复杂对象

Value 和 Array 只能共享 C 基本类型。如果要共享 `dict`、`list` 这种 Python 对象，用 `Manager`：

```python
from multiprocessing import Manager, Process

def worker(shared_dict, shared_list):
    shared_dict['worker_done'] = True
    shared_list.append('result_from_worker')

if __name__ == '__main__':
    with Manager() as manager:
        d = manager.dict()        # 进程间共享的字典
        lst = manager.list()      # 进程间共享的列表

        p = Process(target=worker, args=(d, lst))
        p.start()
        p.join()

        print(d)     # {'worker_done': True}
        print(lst)   # ['result_from_worker']
```

> Manager 底层是一个**独立的代理进程**，所有操作通过代理转发——比共享内存慢，但可以共享任意对象。适合配置信息、缓存等低频访问场景。

### 进程同步：Lock

有了共享内存，就必然有竞争。Lock 保证同一时刻只有一个进程进入临界区：

```python
from multiprocessing import Process, Lock

def printer(lock, msg):
    with lock:                           # acquire + release 自动管理
        for ch in msg:
            print(ch, end='', flush=True)
        print()

if __name__ == '__main__':
    lock = Lock()
    Process(target=printer, args=(lock, 'AAAAAAAAAA')).start()
    Process(target=printer, args=(lock, 'BBBBBBBBBB')).start()
# AAAAAAAAAA
# BBBBBBBBBB   ← 有序输出，不会交叠成 AABBAABB...
```

> Lock 和共享内存的关系：共享内存负责**存**，Lock 负责**保护读写操作互斥**。两者配合使用才能安全地共享数据。

### 练习 1：多进程 vs 单进程性能对比

计算斐波那契数列，对比单进程和 4 进程 `Pool.map()` 的耗时。

```python
import time
from multiprocessing import Pool

def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)

nums = [35, 35, 35, 35]

# 单进程
start = time.time()
results = [fib(n) for n in nums]
print(f'单进程：{time.time() - start:.2f}s')

# 多进程池
if __name__ == '__main__':
    start = time.time()
    with Pool(4) as pool:
        results = pool.map(fib, nums)
    print(f'多进程：{time.time() - start:.2f}s')
```

> [!info]- 预期现象
> 4 核机器上多进程约为单进程的 1/4 耗时，证明了 CPU 密集型任务的并行加速。

### 练习 2：Queue 实现多进程抓取任务

一个进程往队列投放 URL，两个工作进程消费并处理。

```python
from multiprocessing import Process, Queue
import time
import random

def fetcher(q, worker_id):
    while True:
        url = q.get()
        if url is None:
            break
        time.sleep(random.uniform(0.2, 0.5))  # 模拟抓取
        print(f'Worker-{worker_id} 抓取完 {url}')

if __name__ == '__main__':
    q = Queue()
    urls = [f'page_{i}' for i in range(6)]

    # 启动工作进程
    workers = [Process(target=fetcher, args=(q, i)) for i in range(2)]
    for w in workers:
        w.start()

    # 投喂任务
    for url in urls:
        q.put(url)

    # 发送结束信号
    for _ in workers:
        q.put(None)

    for w in workers:
        w.join()
```

> [!info]- 预期输出
> 两个 worker 交替输出抓取结果，每人处理约一半 URL。

### 练习 3：ProcessPoolExecutor + as_completed

用 `ProcessPoolExecutor` 并行下载 4 个"页面"，哪个先完成先输出。

```python
from concurrent.futures import ProcessPoolExecutor, as_completed
import time
import random

def download(page_id):
    delay = random.uniform(0.5, 2.0)
    time.sleep(delay)
    return f'page_{page_id}（耗时 {delay:.1f}s）'

if __name__ == '__main__':
    with ProcessPoolExecutor(max_workers=4) as executor:
        futures = {executor.submit(download, i): i for i in range(4)}

        for f in as_completed(futures):
            print(f.result())  # 先完成的先打印
```

> [!info]- 预期现象
> 输出顺序与提交顺序不一致，短耗时的先打印。

### 练习 4：Lock 保护共享计数器

```python
from multiprocessing import Process, Value, Lock
import time

def add(shared, lock, n):
    for _ in range(n):
        with lock:
            shared.value += 1   # 临界区：读-改-写必须原子

if __name__ == '__main__':
    val = Value('i', 0)
    lock = Lock()

    procs = [Process(target=add, args=(val, lock, 100000)) for _ in range(4)]
    for p in procs: p.start()
    for p in procs: p.join()

    print(val.value)  # 400000（不加锁会少于这个数）
```

> [!info]- 预期输出
> `400000`。不加 Lock 时因竞争条件（race condition），最终值会小于 400000。

## 🤔 常见误区

1. **误区：任何时候都用多进程加速**
   **事实**：进程创建和销毁的开销远大于线程。IO 密集型任务用多线程/协程更合适，只有 CPU 密集型才需要多进程。而且进程数超过 CPU 核数后边际收益递减，上下文切换反而拉低效率。

2. **误区：忘记 `if __name__ == '__main__'`**
   **事实**：Windows 和 macOS 默认使用 `spawn` 启动子进程——即重新导入当前模块并只执行 `target`。没有这行保护，子进程在导入时会再次创建子进程，导致无限递归。Linux 用 `fork` 不会遇到这个问题，但写跨平台代码必须加。

3. **误区：Queue/Pipe 可以传任意对象**
   **事实**：进程间通信依赖 `pickle` 序列化。lambda、生成器、打开的文件句柄等不可 pickle 的对象无法传递。所有传递的数据会在进程间复制一份，大数据结构用共享内存更高效。

4. **误区：`pool.map()` 的参数必须是简单可迭代对象**
   **事实**：`map` 的第二个参数在 `multiprocessing.Pool` 中要求是可迭代且可 pickle 的对象。生成器和 `map` 对象会被 pickle 报错。需要提前转为 `list`。
