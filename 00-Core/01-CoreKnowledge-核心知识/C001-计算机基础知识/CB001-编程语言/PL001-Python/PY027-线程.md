## 📚 核心内容

### 什么是线程

线程是操作系统能调度的**最小执行单元**。一个进程可以包含多个线程，它们共享同一块内存空间（全局变量、文件句柄等），但各自有独立的调用栈。

```
进程 A：
├── 线程 1（主线程）  ← 程序入口，默认有一个
├── 线程 2（工作线程） ← 代码创建的
└── 线程 3（工作线程） ← 代码创建的

进程与线程的关键区别：
  进程之间：内存独立，通信靠 IPC（Queue/Pipe/共享内存）
  线程之间：内存共享，通信靠共享变量 + 锁保护
```

| | 多进程 | 多线程 |
|------|---------|--------|
| 内存 | 独立，不共享 | 共享全局变量 |
| 通信 | IPC（Queue/Pipe） | 共享变量 + Lock |
| 创建开销 | 大（独立内存空间） | 小（只分配栈） |
| GIL 影响 | 不受限制（各有各的 GIL） | 计算密集型无效 |
| 适用 | CPU 密集型 | IO 密集型 |

### GIL 与线程

==GIL（Global Interpreter Lock，全局解释器锁）== 是 CPython 解释器中的一个互斥锁。它保证同一时刻**只有一个线程执行 Python 字节码**——即使你有 8 核 CPU，纯 Python 计算任务用多线程也只能用满 1 核。

```python
import threading
import time

def count(n):
    while n > 0:
        n -= 1

# 单线程
start = time.time()
count(100_000_000)
print(f'单线程：{time.time() - start:.2f}s')

# 双线程（计算密集型 — GIL 拖后腿）
start = time.time()
t1 = threading.Thread(target=count, args=(50_000_000,))
t2 = threading.Thread(target=count, args=(50_000_000,))
t1.start(); t2.start()
t1.join(); t2.join()
print(f'双线程：{time.time() - start:.2f}s')   # 不会比单线程快，甚至更慢
```

**GIL 之谜：为什么线程切换了，速度反而更慢？**

上面的例子中，CPU 在 `t1` 和 `t2` 之间反复切换——每次切换都需要保存/恢复线程上下文，切换本身就有开销。但由于 GIL 的存在，**切来切去只有一个人干活，另一个人干瞪眼**——纯属空转。切换开销是额外白费的，总时间 = 两个任务串行计算时间 + N 次上下文切换时间，所以比干脆一个人一口气干完更慢。

| 场景 | 多线程有用吗 | 原因 |
|------|------------|------|
| 纯 Python 计算（循环、加减） | ❌ 没用 | GIL 串行化，线程切换纯浪费 |
| 文件读写、网络请求 | ✅ 有用 | IO 等待时会释放 GIL，让别的线程干活 |
| 调用 C 扩展（numpy、OpenCV） | ✅ 有用 | C 代码可主动释放 GIL |

> GIL 只在 CPython 中有。Jython（Java 实现）和 IronPython（.NET 实现）没有 GIL。Python 3.13 引入的实验性 free-threaded 模式允许禁用 GIL，但目前生态还不成熟。

### 创建线程

```python
import threading
import time

def worker(name, delay):
    print(f'线程 {name} 开始')
    time.sleep(delay)              # sleep 释放 GIL，其他线程可以跑
    print(f'线程 {name} 结束')

# 创建线程
t1 = threading.Thread(target=worker, args=('A', 2))
t2 = threading.Thread(target=worker, kwargs={'name': 'B', 'delay': 1})

t1.start()                         # 启动（非阻塞，主线程继续往下）
t2.start()

t1.join()                          # 等待 t1 结束
t2.join()                          # 等待 t2 结束

print('所有线程已完成')
# 输出顺序：B 结束（delay短）→ A 结束 → 所有线程已完成
```

> 线程的 `start()` 和 `join()` 用法与上节 [[PY026-进程]] 的 `Process` 完全一致，切换进程和线程只需改导入的类名。

### daemon 线程

当 `daemon=True` 时，该线程变为**守护线程**——主线程退出时，守护线程自动被杀死，不管它干没干完：

```python
def background_task():
    while True:
        print('心跳...')
        time.sleep(1)

t = threading.Thread(target=background_task, daemon=True)
t.start()
time.sleep(3)
print('主线程退出')   # 守护线程随之结束，不会阻止程序退出
```

| 属性 | 行为 |
|------|------|
| `daemon=False`（默认） | 主线程会等它结束才退出 |
| `daemon=True` | 主线程退出时直接杀掉它 |

> 典型用途：后台日志刷新、心跳检测、定时清理任务。核心业务线程不要设 daemon——程序退出时可能丢了正在处理的数据。

### 继承式创建（子类化 Thread）

```python
class FetchThread(threading.Thread):
    def __init__(self, url):
        super().__init__()
        self.url = url
        self.result = None

    def run(self):
        print(f'正在请求 {self.url}')
        time.sleep(1)     # 模拟 IO
        self.result = f'{self.url} 的响应数据'

t = FetchThread('https://api.example.com')
t.start()
t.join()
print(t.result)
```

### 竞态条件与 Lock

多个线程同时读写一个共享变量，不保护就会出问题：

```python
import threading

counter = 0

def increment():
    global counter
    for _ in range(100000):
        # counter += 1 不是原子操作
        # 拆开 = 读 counter → 加 1 → 写回 counter
        # 线程可能在「读」之后被切换，另一线程改过 counter
        # 导致写回时覆盖了对方的修改
        temp = counter
        temp = temp + 1
        counter = temp

threads = [threading.Thread(target=increment) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()

print(counter)  # 远小于 400000（每次都不同，竞态条件）
```

==竞态条件（Race Condition）== 就是多个线程并发访问同一数据，最终结果取决于线程调度的时序——这种 bug 难以复现、难以调试。解决方案是加 **Lock**，把读-改-写变成原子操作：

```python
lock = threading.Lock()
counter = 0

def increment():
    global counter
    for _ in range(100000):
        with lock:                   # 同一时刻只有一个线程能进入
            counter += 1

# 4 线程各加 10 万次 → 40 万 ✅
```

**`Lock` vs `RLock`**：

```python
# Lock — 不可重入（同一线程 acquire 两次 = 死锁）
lock = threading.Lock()
lock.acquire()
lock.acquire()   # ❌ 死锁！等自己释放，但自己卡在 acquire 上

# RLock — 可重入（同一线程可多次 acquire，配对 release 即可）
rlock = threading.RLock()
rlock.acquire()
rlock.acquire()   # ✅ 计数器 +1
rlock.release()
rlock.release()   # 计数归零，锁释放
```

> `RLock` 在递归函数、或在 A 方法加锁后内部调用了也加锁的 B 方法时非常有用。简单的临界区保护用 `Lock` 就够。

### 线程安全队列：queue.Queue

手动加锁容易出错——少解锁一次就死锁，锁的范围大了又影响性能。`queue.Queue` 内置线程安全，是最优雅的线程间通信方式：

```python
import threading
import queue
import time

def producer(q):
    for i in range(5):
        time.sleep(0.5)
        q.put(f'任务_{i}')           # 放入队列（线程安全）
    q.put(None)                     # 结束信号

def consumer(q, name):
    while True:
        item = q.get()               # 取出（队列空则阻塞等待）
        if item is None:
            q.put(None)              # 把结束信号放回去，让其他消费者也能收到
            break
        print(f'{name} 处理 {item}')
        q.task_done()                # 标记此任务完成

q = queue.Queue()
threading.Thread(target=producer, args=(q,)).start()
threading.Thread(target=consumer, args=(q, 'Worker-1')).start()
threading.Thread(target=consumer, args=(q, 'Worker-2')).start()
```

`queue.Queue` 常用方法：

| 方法 | 行为 |
|------|------|
| `put(item)` | 放入（队满则阻塞） |
| `put(item, timeout=3)` | 放入，超时抛 `queue.Full` |
| `get()` | 取出（队空则阻塞） |
| `get(timeout=3)` | 取出，超时抛 `queue.Empty` |
| `task_done()` | 标记一个任务已完成（配合 `join()` 使用） |
| `q.join()` | 阻塞直到队列中所有任务都被 `task_done()` |

> 线程间通信的黄金法则：**优先用 `queue.Queue`，不要手动 `Lock` + 共享列表**。Queue 把所有边界条件（空等待、满阻塞、线程安全）都帮你搞定了。

### ThreadPoolExecutor

> 💡 这个知识点正是 [[PY026-进程]] 的 📝 待补充内容——[[PY026-进程]] 中 `ProcessPoolExecutor` 已经介绍，此处补全 `ThreadPoolExecutor`，两者 API 完全统一。需要我把 PY026 的线程待办项也一起处理掉吗？

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time
import random

def fetch(url):
    delay = random.uniform(0.5, 2.0)
    time.sleep(delay)
    return f'{url} → {delay:.1f}s'

urls = [f'/api/user/{i}' for i in range(10)]

with ThreadPoolExecutor(max_workers=3) as executor:
    # 方式一：submit + as_completed（不保证顺序，先完成的先处理）
    futures = {executor.submit(fetch, url): url for url in urls}
    for f in as_completed(futures):
        print(f.result())

    # 方式二：map（保持顺序，等价于 for url in urls: executor.submit(fetch, url)）
    # for result in executor.map(fetch, urls):
    #     print(result)
```

> `ThreadPoolExecutor` 和 `ProcessPoolExecutor` API 完全一致——切换线程池和进程池只需改类名，`max_workers` 从 CPU 核数改成 IO 并发数。

### threading.local()

线程间共享全局变量很麻烦（要加锁），但完全不共享又有数据传递问题。`threading.local()` 让每个线程拥有同名但独立的变量副本：

```python
import threading

thread_data = threading.local()

def process():
    # 每个线程独立设置和读取自己的 thread_data.user_id
    thread_data.user_id = threading.current_thread().name
    print(f'{threading.current_thread().name}: user_id = {thread_data.user_id}')

threads = [threading.Thread(target=process) for _ in range(3)]
for t in threads: t.start()
for t in threads: t.join()
# Thread-1: user_id = Thread-1
# Thread-2: user_id = Thread-2
# Thread-3: user_id = Thread-3
```

> 典型的应用场景：Web 框架中每个请求由一个线程处理，用 `threading.local()` 存储当前请求的用户信息、数据库 Session，线程之间不干扰。

### 练习 1：多线程下载模拟

用 `ThreadPoolExecutor` 并发"下载"10 个 URL，限制最大并发为 3。

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time
import random

def download(url):
    delay = random.uniform(0.3, 1.5)
    time.sleep(delay)
    return f'{url} 下载完成（{delay:.1f}s）'

urls = [f'page_{i}.html' for i in range(10)]

with ThreadPoolExecutor(max_workers=3) as executor:
    futures = {executor.submit(download, url): url for url in urls}
    for f in as_completed(futures):
        print(f.result())
```

> [!info]- 预期现象
> 输出顺序和提交顺序不一致，耗时短的先打印。观察总耗时——10 个任务、3 个并发组，大约等于 4 轮串行的耗时。

### 练习 2：Lock 修复竞态条件

先用不加锁的代码看 bug，再加 Lock 修复。

```python
import threading

counter = 0
lock = threading.Lock()

def unsafe_increment():
    global counter
    for _ in range(100000):
        counter += 1          # 不加锁 → 竞态条件

def safe_increment():
    global counter
    for _ in range(100000):
        with lock:            # 加锁 → 安全
            counter += 1

# 对比实验
for name, func in [('不加锁', unsafe_increment), ('加锁', safe_increment)]:
    counter = 0
    threads = [threading.Thread(target=func) for _ in range(4)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(f'{name}：counter = {counter}（期望 400000）')
```

> [!info]- 预期输出
> ```
> 不加锁：counter = 284713（每次不同，小于 400000）
> 加锁：counter = 400000
> ```

### 练习 3：Queue 生产者-消费者

```python
import threading
import queue
import time
import random

def producer(q, items):
    for item in items:
        time.sleep(random.uniform(0.1, 0.3))
        q.put(item)
        print(f'生产：{item}')
    q.put(None)  # 结束信号

def consumer(q, name):
    while True:
        item = q.get()
        if item is None:
            q.put(None)  # 转发结束信号
            break
        time.sleep(random.uniform(0.2, 0.5))
        print(f'{name} 消费：{item}')
        q.task_done()

q = queue.Queue()
items = ['A', 'B', 'C', 'D', 'E', 'F']

threading.Thread(target=producer, args=(q, items)).start()
threading.Thread(target=consumer, args=(q, 'Worker-1')).start()
threading.Thread(target=consumer, args=(q, 'Worker-2')).start()
```

> [!info]- 预期现象
> 两个消费者交替取出任务处理，生产完一个就消费一个，而不是全生产完再开始。

## 🤔 常见误区

1. **误区：开了多线程就一定会加速**
   **事实**：计算密集型任务受 GIL 限制，多线程不仅不能加速，线程切换的开销反而让总耗时更长（比单线程还慢）。只有 IO 密集型（网络、文件、sleep）才受益于多线程——IO 等待时 GIL 被释放，其他线程可以跑。

2. **误区：`Lock` 和 `RLock` 通用**
   **事实**：`Lock` 不可重入——同一线程连续 `acquire()` 两次会死锁。递归函数或间接调用自己的方法必须用 `RLock`。

3. **误区：不用 join 也能正常拿到结果**
   **事实**：主线程不 `join()` 就直接打印 `thread.result` 时，工作线程可能还没跑完，拿到的可能是 `None`（不管子线程死活就往下走）。`join()` 确保子线程跑完再继续。

4. **误区：Queue 取了数据后原队列长度就减 1 了**
   **事实**：`get()` 确实移除了数据，队列长度减 1。但 `task_done()` 是独立的计数器——用于 `join()` 判断所有任务是否已处理完，和队列实际大小无关。

5. **误区：用 `list` + `Lock` 也能替代 Queue**
   **事实**：能，但 Queue 内置的条件变量和等待通知机制避免了轮询（while 循环不停检查 list 是否非空），CPU 空转的轮询远不如 Queue 的阻塞等待高效。
