## 📚 核心内容

单元测试就是**为单个函数/类写一段"验证代码"**，自动检查它是否符合预期。写测试不是负担，而是给自己上的三道保险：

1. **回归防护**——改了代码，跑一遍测试就知道有没有改坏老功能；
2. **活文档**——测试用例本身就说明了"这个函数该怎么用、边界是什么"；
3. **强迫思考**——写测试时得想清楚输入输出的边界，提前暴露设计问题。

Python 生态里最主流的是 **pytest**，比标准库 `unittest` 简洁得多——核心只有一个 `assert`。

### 安装与基本断言

```bash
pip install pytest
```

写测试就是写普通的 Python 函数，名字以 `test_` 开头，函数体里用 `assert` 断言：

```python
# test_math.py
def add(a, b):
    return a + b

def test_add():
    assert add(1, 2) == 3          # ✅ 通过
    assert add(-1, 1) == 0         # ✅ 通过
    assert add(0, 0) == 0          # ✅ 通过

def test_add_str():
    assert add("a", "b") == "ab"   # 字符串拼接
```

```bash
pytest test_math.py
# ===== 2 passed in 0.01s =====
```

> pytest 直接用 `assert`，不需要 `unittest` 里 `self.assertEqual(a, b)` 那套啰嗦写法。断言失败时 pytest 会自动展开两边值，告诉你差在哪。

**断言失败长什么样**：

```python
def test_add():
    assert add(1, 2) == 4   # 故意写错
```

```bash
pytest test_math.py
# FAILED test_math.py::test_add - assert 3 == 4
# E   assert 3 == 4
```

### 测试发现规则

pytest 不需要注册，它会**自动发现**符合命名规则的测试。默认规则：

| 维度 | 规则 |
|------|------|
| 文件名 | `test_*.py` 或 `*_test.py` |
| 函数名 | `test_*` |
| 类名 | `Test*`（类不能有 `__init__`） |
| 类内方法 | `test_*` |

```python
# test_user.py
def test_login(): ...          # ✅ 会被发现

class TestUser:
    def test_register(self): ...   # ✅ 会被发现
    def helper(self): ...          # ❌ 不是 test_ 开头，跳过

def login(): ...               # ❌ 不是 test_ 开头，跳过
```

```bash
pytest                # 不加参数，自动扫描当前目录下所有测试
pytest test_user.py   # 指定文件
pytest -k "login"     # 只跑名字里含 login 的测试
pytest -v             # 详细输出，列出每个测试
pytest -s             # 显示测试里的 print 输出
```

### fixture：测试的前置准备与复用

![[90-Storage/98-Asset-资源/InfoGraphic/PY030-单元测试/Python单元测试fixture流程-信息图-v1.png]]

很多测试开始前需要"准备环境"（连数据库、造数据、登录），结束后还要"清理"。**fixture** 就是把这套准备/清理逻辑抽出来复用：

```python
import pytest

@pytest.fixture
def db():
    # --- 前置准备 ---
    conn = connect_database()
    conn.create_table("users")
    yield conn            # yield 的值就是测试函数收到的参数
    # --- 后置清理（测试结束后执行） ---
    conn.close()

def test_insert(db):      # 参数名 = fixture 名
    db.insert("users", {"name": "Alice"})
    assert db.count("users") == 1

def test_query(db):
    db.insert("users", {"name": "Bob"})
    assert db.query("users")[0]["name"] == "Bob"
```

> **`yield` 之前 = 准备，`yield` 之后 = 清理**。即使测试失败抛异常，`yield` 之后的清理代码也会执行（fixture 内部用 try/finally 保证）。这和 [[PY023-错误类型与异常处理机制]] 里的 `with` 上下文管理器是同一套思想。

#### fixture 的注入规则：只对 pytest 管理的函数生效

fixture 靠「**参数名 = fixture 名**」自动注入，但**只注入到 pytest 自己调用的函数**上——测试函数、fixture 函数、钩子函数。测试函数体里你自己写的普通辅助函数，pytest 看不见，参数**不会**自动填充，必须手动传：

```python
def test_insert(db):                 # ✅ db 自动注入（test_insert 是 pytest 管理的）
    assert insert_user(db, "Alice")  # ❌ 内层函数必须手动把 db 传进去

def insert_user(db, name):           # 普通函数，pytest 不管理，参数不自动填
    db.insert("users", {"name": name})
    return db.count("users") == 1
```

想让辅助函数也自动拿到 `db`？把它也升格成 fixture——fixture 的参数同样是自动注入的：

```python
@pytest.fixture
def insert_user(db):                 # ✅ fixture 的参数也按名字自动注入 db
    def _insert(name):
        db.insert("users", {"name": name})
        return db.count("users") == 1
    return _insert

def test_insert(insert_user):        # ✅ 注入 insert_user（它内部已拿到 db）
    assert insert_user("Alice")
```

> 规则：**自动注入靠名字匹配，但只在 pytest 管理的函数身上生效。** 自己写的辅助函数是"圈外人"，一律手动传参；想要自动注入就把它做成 fixture。

#### yield 的驱动原理：pytest 用 `next()` 走走停停

fixture 本质是一个**生成器**（含 `yield` 的函数都是生成器）。pytest 在背后用 `next()` 驱动它，测试结束时再 `next()` 一次，让清理代码执行：

```python
# pytest 驱动 fixture 的简化过程（概念等价，非真实源码）：
gen = db()                 # ① 调用 fixture → 拿到生成器，此时还没执行任何代码
conn = next(gen)           # ② 第一次 next：执行到 yield，暂停，拿到 conn
try:
    test_insert(conn)      # ③ 把 conn 当 db 传给测试，跑测试
finally:
    try:
        next(gen)          # ④ 第二次 next：从 yield 之后继续 → conn.close()
    except StopIteration:
        pass               # 函数体跑完，正常结束
```

| 步骤 | 谁驱动 | 发生什么 |
|------|--------|----------|
| ① `gen = db()` | pytest | 拿到生成器对象，**代码还没跑** |
| ② `next(gen)` | pytest | 跑到 `yield conn`，**暂停**，返回 `conn` |
| ③ 跑测试 | pytest | `conn` 作为 `db` 参数执行测试 |
| ④ `next(gen)` | pytest | **恢复**，从 `yield` 下一行跑 `conn.close()` |
| ⑤ `StopIteration` | 生成器 | 函数体走完，自然结束 |

> **触发清理的，是 pytest 在测试结束后的第二次 `next()`**——它包在 `finally` 里，所以测试哪怕断言失败、抛异常，`conn.close()` 一定跑得到。这套「`yield` 前准备 / `yield` 后清理」正是 [[PL-PY-012-可迭代对象与迭代器协议]] 里生成器机制的工程化应用。

**fixture 的 scope（作用范围）**：

| scope | 创建时机 | 适用场景 |
|-------|----------|----------|
| `function`（默认） | 每个测试函数都新建一次 | 需要隔离的临时数据 |
| `module` | 每个测试文件建一次 | 本文件共享的连接 |
| `session` | 整个测试会话建一次 | 昂贵的全局资源 |

```python
@pytest.fixture(scope="module")
def db_conn():
    conn = connect_database()
    yield conn
    conn.close()
# 本模块所有测试共享同一个 conn，省去反复建连
```

### 参数化：`@pytest.mark.parametrize`

同一个测试逻辑，要对多组输入跑一遍，不用复制粘贴，用 `parametrize`：

```python
import pytest

def add(a, b):
    return a + b

@pytest.mark.parametrize("a,b,expected", [
    (1, 2, 3),
    (-1, 1, 0),
    (0, 0, 0),
    (100, 200, 300),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

```bash
pytest test_math.py -v
# test_math.py::test_add[1-2-3] PASSED
# test_math.py::test_add[-1-1-0] PASSED
# test_math.py::test_add[0-0-0] PASSED
# test_math.py::test_add[100-200-300] PASSED
```

> 一组参数就是一个独立的测试用例，某组失败不会影响其他组，报错时直接指出是哪组参数。

### 异常测试：`pytest.raises`

测试"该报错的时候确实报错了"：

```python
import pytest

def divide(a, b):
    if b == 0:
        raise ValueError("除数不能为 0")
    return a / b

def test_divide_by_zero():
    with pytest.raises(ValueError):      # 期望抛出 ValueError
        divide(1, 0)

def test_divide_error_message():
    with pytest.raises(ValueError, match="除数"):   # 还能匹配错误信息
        divide(1, 0)
```

> 如果 `divide(1, 0)` 没有抛异常，或抛的不是 `ValueError`，这个测试就失败——`pytest.raises` 能确认"异常类型对不对、错误信息对不对"。

### mock：替换外部依赖

单元测试要"快"和"稳"，不能真的连数据库、发邮件、调第三方 API。**mock** 用假对象替换真实依赖，让测试不碰外部环境：

```python
# myapp.py
import requests

def is_online():
    resp = requests.get("https://api.example.com/status")
    return resp.json()["status"] == "ok"
```

```python
# test_myapp.py
from unittest.mock import Mock, patch
import myapp

def test_is_online():
    # 用假对象替换 requests.get，避免真实网络请求
    fake_resp = Mock()
    fake_resp.json.return_value = {"status": "ok"}

    with patch("myapp.requests.get", return_value=fake_resp):
        assert myapp.is_online() is True
```

#### `return_value` 的双重形态：关键字参数 vs 属性

`return_value` 是 mock 框架规定好的一个名字，专门放「假对象被调用时的返回值」。它有两种写法，指向同一件事：

```python
# 形态一：关键字参数（构造 mock 时直接设）
Mock(return_value=fake_resp)

# 形态二：属性（事后赋值）
m = Mock()
m.return_value = fake_resp
```

两行效果一样。上面的例子里两种形态都出现了：

- `fake_resp.json.return_value = {...}` —— **属性**赋值，让 `fake_resp.json()` 返回这个字典；
- `patch("...", return_value=fake_resp)` —— **关键字参数**，让替换进去的假对象一被调用就返回 `fake_resp`。

> `return_value` 不是你需要预先声明的变量，它只是 `Mock` / `patch` 提供的关键字参数名（也是 mock 对象上的属性名）。

#### `patch` 到底做了什么

`with patch(...)` 等价于「保存真对象 → 换成假的 → 测试 → 还原」四步：

```python
real_get = myapp.requests.get        # ① 保存真的
myapp.requests.get = fake_resp       # ② 换成假的
try:
    assert myapp.is_online() is True # ③ 测试（现在用的是假的）
finally:
    myapp.requests.get = real_get    # ④ 无论如何都还原
```

> **目标路径要写「被测模块里的名字」**（`myapp.requests.get`），不是定义处（`requests.get`）——`is_online` 是在 `myapp` 里通过 `requests.get` 调用的，所以要 patch `myapp.requests.get`。

**pytest 内置的 `monkeypatch` fixture** 更简单：

```python
def test_is_online(monkeypatch):
    fake_resp = Mock()
    fake_resp.json.return_value = {"status": "ok"}
    monkeypatch.setattr("myapp.requests.get", lambda url: fake_resp)
    assert myapp.is_online() is True
```

> **mock 的核心思想**：把"慢的、不稳定的、有副作用的"依赖换掉，只测你自己的逻辑。这样测试秒跑、可重复、不会真的发出邮件。

### `monkeypatch`：pytest 内置补丁工具

pytest 内置了 `monkeypatch` fixture，它的功能和 `@patch` 完全一致，都是用来临时替换对象/函数/属性，测试结束后自动恢复。

#### `monkeypatch` 基本用法

```python
def test_get_user_input(monkeypatch):
    # mock 内置 input，让它每次都返回我们预设的值
    monkeypatch.setattr('builtins.input', lambda _: "42")
    assert get_user_guess() == 42
```

和 `@patch` 一样，`setattr` 的第二个参数就是你要替换成的**新值**，可以是任意类型：
- 如果替换函数，就传一个新的 mock 函数
- 如果替换变量，就传对应类型的值：
```python
# 把模块里的 MAX_RETRIES 替换成 1
monkeypatch.setattr('my_module.MAX_RETRIES', 1)
# 把模块里的默认配置替换成我们的测试配置
monkeypatch.setattr('my_module.DEFAULT_CONFIG', {'timeout': 5})
```

#### 为什么只需要调用一次 `setattr`，就能处理多次输入？

很多人会疑惑：为什么在循环获取用户输入的场景下，只调用一次 `setattr` 就可以接受多次输入？

这是因为：`monkeypatch.setattr` 替换的是**函数对象本身**，不是函数的一次调用。

举个例子：我们给井字棋测试 mock 了 `input`：
```python
def test_cell_already_occupied(self, monkeypatch):
    calls = []
    def mock_input(_):
        calls.append(1)
        return "1 1"
    monkeypatch.setattr('builtins.input', mock_input)  # ← 只调用一次
    # ...
```

当我们执行 `monkeypatch.setattr('builtins.input', mock_input)` 时：
1. 它会把 Python 全局的 `input` 函数**整个替换成你写的 `mock_input`**
2. 替换完成后，在当前测试运行期间，**任何地方对 `input()` 的调用，都会自动执行你的 `mock_input` 函数**
3. `get_move` 循环内每次调用 `input()`，都会走我们的 mock 函数，所以当然可以处理多次输入
4. 测试结束后，pytest 自动帮你把 `input` 恢复成原来的内置实现

所以，**只需要调用一次 `setattr`，替换完成后，所有后续调用都会走你的新函数**，不需要循环调用 `setattr`。就像换门锁一样，换一次就够了，之后每次开门都用新钥匙。

#### 那个错误的测试用例说明了什么？

我们来看井字棋测试里一个有问题的写法：
```python
def test_cell_already_occupied(self, monkeypatch):
    board = create_board()
    board[0][0] = 'X'  # 位置已经被占
    calls = []
    def mock_input(_):
        calls.append(1)
        return "1 1"  # ← 每次调用都返回被占的坐标
    monkeypatch.setattr('builtins.input', mock_input)
    row, col = get_move(board, "O")
    assert len(calls) == 2  # ← 这里断言调用两次
    assert row == 0
    assert col == 0
```

这个测试如果 `get_move` 逻辑正确（一直重试直到拿到合法输入），那它会**死循环**：
- 第一次调用 `input`，返回 `1 1`，检查发现位置被占，重试
- 第二次调用 `input`，还是返回 `1 1`，还是被占，继续重试
- ... 永远循环下去，永远不会返回

所以正确的测试应该怎么写？需要让 mock 函数第一次返回非法值，第二次返回合法值：
```python
def test_cell_already_occupied(self, monkeypatch):
    board = create_board()
    board[0][0] = 'X'
    calls = []
    def mock_input(_):
        calls.append(1)
        if len(calls) == 1:
            return "1 1"  # 第一次返回非法值
        else:
            return "2 2"  # 第二次返回合法值
    monkeypatch.setattr('builtins.input', mock_input)
    row, col = get_move(board, "O")
    assert len(calls) == 2  # ← 验证确实重试了一次
    assert row == 1
    assert col == 1  # ← 验证拿到了第二次的合法值
```

#### `@patch` (unittest.mock) vs `monkeypatch` (pytest) 对比

| | `@patch` | `monkeypatch` |
|---|---|---|
| 来源 | Python 标准库 `unittest.mock` | pytest 官方内置 |
| 典型用法 | 通常作为装饰器作用在整个测试函数 | 作为参数注入测试函数，可在函数内局部打补丁 |
| 灵活性 | 补丁只能作用在整个测试函数 | 可以在任意位置打补丁，支持局部替换 |
| 自动恢复 | 测试结束自动恢复 | 测试结束自动恢复 |
| 功能等价性 | ✅ 都能实现打补丁功能 | ✅ 都能实现打补丁功能 |

简单来说：两者功能完全一样，都是打补丁，只是使用方式不同。`monkeypatch` 更灵活，代码可读性更好，是 pytest 里更推荐的写法。

### `@patch` 参数详解

#### `side_effect`：多次调用按顺序返回

当被 mock 的函数需要**多次调用返回不同结果**（比如多次 `input()`），用 `side_effect` 按调用顺序给返回值：
```python
# 输入非法两次，第三次才输入合法，验证会不会一直重试到拿到合法值
@patch('builtins.input', side_effect=['abc', 'def', '42'])
def test_invalid_input_retries(mock_input):
    result = get_user_guess()
    assert result == 42
    assert mock_input.call_count == 3  # 验证调用了三次
```
每次调用 `input()` 会依次返回列表里的值，完全模拟用户多次输入，不需要人工干预就能自动化测试。如果调用次数比给的值多，会抛 `StopIteration`，测试自然失败，正好帮你发现问题。

#### `return_value` vs `side_effect`

| 参数 | 使用场景 |
|------|----------|
| `return_value=x` | 不管调用多少次，永远返回同一个值 `x` |
| `side_effect=[a, b, c]` | 每次调用依次返回列表里的值，适合模拟多次输入、多轮调用 |

#### `assert_called_once()`：验证调用次数

mock 对象自带断言方法，验证行为对不对：

| 断言方法 | 作用 |
|----------|------|
| `mock.assert_called_once()` | 正好被调用一次 |
| `mock.assert_called()` | 至少被调用一次 |
| `mock.assert_not_called()` | 一次都没被调用过 |
| `mock.assert_called_once_with(args...)` | 正好被调用一次，并且参数就是 `args...` |
| `mock.call_count` | 返回调用次数，用来断言调用了多少次 |

> 只有被 `patch` 替换过的 mock 对象才有这些断言方法，普通对象没有。

### 实例：猜数字游戏单元测试

猜数字游戏拆分了三个函数，我们给每个函数写测试，mock 掉依赖：

```python
"""
单元测试：猜数字游戏
分步运行：pytest -m "taskno=N" -v （N 是任务号）
"""

import pytest
from unittest.mock import patch
from guess_number_game import (
    generate_number,
    get_user_guess,
    play_one_round
)


@pytest.mark.task(taskno=1)
class TestGenerateNumber:
    """任务 1：测试 generate_number 函数"""

    def test_returns_integer_in_range(self):
        """测试返回值是指定范围内的整数"""
        for _ in range(100):  # 多次测试避免概率问题
            num = generate_number(0, 100)
            assert isinstance(num, int)
            assert 0 <= num <= 100

    def test_custom_range_works(self):
        """测试自定义范围也能正常工作"""
        for _ in range(100):
            num = generate_number(10, 20)
            assert 10 <= num <= 20


@pytest.mark.task(taskno=2)
class TestGetUserGuess:
    """任务 2：测试 get_user_guess 函数"""

    @patch('builtins.input', side_effect=['50'])
    def test_valid_input_returns_integer(self, mock_input):
        """测试合法输入返回正确整数"""
        result = get_user_guess()
        assert result == 50
        mock_input.assert_called_once()

    @patch('builtins.input', side_effect=['abc', 'def', '42'])
    def test_invalid_input_retries(self, mock_input):
        """测试非法输入会一直要求重试，直到拿到合法数字"""
        result = get_user_guess()
        assert result == 42
        # 调用了三次 input，说明重试了两次
        assert mock_input.call_count == 3

    @patch('builtins.input', side_effect=['-1'])
    def test_minus_one_returns_immediately(self, mock_input):
        """测试输入 -1 直接返回，不做范围检查"""
        result = get_user_guess()
        assert result == -1
        mock_input.assert_called_once()


@pytest.mark.task(taskno=3)
class TestPlayOneRound:
    """任务 3：测试 play_one_round 函数"""

    @patch('guess_number_game.get_user_guess', side_effect=[50, 25, 12, 42])
    def test_correct_guess_returns_guess_count(self, mock_guess):
        """测试猜对了返回正确的猜测次数"""
        # mock random 固定生成答案 42，不用随机
        with patch('guess_number_game.generate_number', return_value=42):
            count = play_one_round()
            assert count == 4
            assert mock_guess.call_count == 4

    @patch('guess_number_game.get_user_guess', return_value=-1)
    def test_user_exits_returns_zero(self, mock_guess):
        """测试用户中途退出返回 0"""
        with patch('guess_number_game.generate_number', return_value=42):
            count = play_one_round()
            assert count == 0
            assert mock_guess.called_once()

    @patch('guess_number_game.get_user_guess', side_effect=[10, 20, 30, 40, 50, 42])
    @patch('builtins.print')
    def test_prints_prompts_correctly(self, mock_guess, mock_print):
        """测试游戏过程正确打印提示信息"""
        with patch('guess_number_game.generate_number', return_value=42):
            play_one_round()
            # 至少会打印 "恭喜猜对了" 和 "太小了"，验证确实打印了
            assert any("恭喜" in str(call) for call in mock_print.call_args_list)
            assert any("太小" in str(call) for call in mock_print.call_args_list)
```

- 每个任务一个 class，用 `@pytest.mark.task(taskno=N)` 标记，可以分步测试：`pytest -m "taskno <= 2" -v` 做完前两步跑前两步
- `patch` 可以当装饰器用，也可以当上下文管理器用：整个测试都要替换就当装饰器，只在函数内一块替换就用 `with patch(...)`
- `any(...)` 用来验证至少打印过一次关键信息，比如猜对了一定打印"恭喜"

## 🤔 常见误区

1. **误区：「测试要 100% 覆盖所有分支才算合格」**
   **事实**：覆盖率是参考不是目标。追求 100% 常常逼出大量无意义的测试，还拖慢开发。优先覆盖核心逻辑、边界条件、易错路径，而不是每条 `else` 都测。

2. **误区：「`assert` 会被 `python -O` 关闭，测试会失效」**
   **事实**：pytest 在收集测试时会**重写 assert 语句**，不受 `-O` 优化模式影响。所以测试里的 `assert` 永远生效（生产代码里才要小心 `-O`，见 [[PY023-错误类型与异常处理机制]]）。

3. **误区：「测试里 `print` 看不到，就没法调试」**
   **事实**：pytest 默认会**吞掉**测试里的 `print` 输出（为了结果清爽）。加 `-s` 参数就能看到：`pytest -s`。

4. **误区：「fixture 就是个普通函数」**
   **事实**：fixture 有普通函数没有的三样东西：**依赖注入**（测试函数声明同名参数自动拿到）、**scope**（控制生命周期）、**`yield` 后的清理**（保证资源释放）。普通函数没有这些语义。

5. **误区：「mock 是骗人的，测出来的不算数」**
   **事实**：mock 测的不是"外部依赖对不对"，而是"你自己的逻辑在依赖返回某结果时行为正不正确"。外部依赖的真伪由**集成测试**去验证，单元测试和它分工不同。

## 🎯 `@pytest.mark`：给测试打标记分组

pytest 允许你给测试打**标记（mark）**，方便按条件筛选运行测试。最常用的场景就是**分步练习题**：

### `@pytest.mark.task`：分步练习标记

做编程练习题时，题目通常分步要求实现，给每一步的测试打上 `@pytest.mark.task(taskno=N)` 标记，做完一步只跑这一步测试：

```python
import pytest

@pytest.mark.task(taskno=1)
class TestGenerateNumber:
    """第一步：实现 generate_number"""
    def test_xxx(self): ...

@pytest.mark.task(taskno=2)
class TestGetUserGuess:
    """第二步：实现 get_user_guess"""
    def test_xxx(self): ...
```

运行方式：
```bash
# 只跑第一步的测试
pytest -m "taskno=1" -v

# 跑完前两步，都验证一下
pytest -m "taskno <= 2" -v
```

### 标记加在哪里？

两种方式都可以，看你怎么组织测试：
| 加在... | 适用场景 |
|---------|---------|
| **测试类上面** | 整个 class 都是同一个任务 → 一个 class 对应一个任务 |
| **测试方法上面** | 同一个 class 里有多个不同任务的测试 → 每个方法单独标记 |

pytest 都能正确识别，筛选规则也都生效。

### 更多标记用法

标记还可以用来做很多事，比如：
- `@pytest.mark.slow` 标记慢测试，平时可以跳过：`pytest -m "not slow"`
- `@pytest.mark.parametrize` 是参数化标记，前面已经讲过
- 自定义任意标记，按你的需求分组筛选

## 📊 查看测试覆盖率

写完测试后，我们经常想知道**哪些代码已经被测试覆盖，哪些还没被测试**，这就是「覆盖率」告诉我们的事。常用工具是 `pytest-cov`。

### 安装
```bash
pip install pytest-cov
```

### 生成报告
```bash
# 在项目根目录运行
pytest --cov=./ --cov-report=html
```

这个命令会：
1. 运行所有测试
2. 统计每个文件的覆盖情况
3. 生成 `htmlcov/` 目录，里面是完整的 HTML 覆盖率报告

### 在 VS Code 中查看

#### 方式一：打开 HTML 报告（最简单）
1. 运行完上面命令后，在 VS Code 文件浏览器找到 `htmlcov/index.html`
2. 右键 → "Open in Default Browser"
3. 在浏览器中可以：
   - 看整体覆盖率百分比
   - 点击具体文件，绿色 = 已覆盖，红色 = 未覆盖

#### 方式二：使用 Coverage Gutters 插件（编辑器内直接看）
1. 在 VS Code 扩展市场搜索安装 **Coverage Gutters** 插件
2. 运行测试同时生成 XML 格式报告：
   ```bash
   pytest --cov=./ --cov-report=xml
   ```
3. 按 `Ctrl+Shift+P` 打开命令面板，输入 `Coverage Gutters: Watch`
4. 打开你的代码文件，编辑器左侧会直接显示：
   - 绿色对勾 = 该行已覆盖
   - 红色叉号 = 该行未覆盖
