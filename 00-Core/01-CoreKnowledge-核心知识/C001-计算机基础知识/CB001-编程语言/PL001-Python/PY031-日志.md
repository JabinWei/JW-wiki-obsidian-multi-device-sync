## 📚 核心内容

程序跑起来后，光靠肉眼盯着输出是不行的——**日志**就是程序运行过程中留下的"脚印"，用来追踪发生了什么、哪里出了问题。

初学最自然的做法是用 `print`，但它有致命缺陷：

| 维度 | `print` | `logging` |
|------|---------|-----------|
| 级别 | 无法区分"调试信息"和"严重错误" | 5 个级别，按需开关 |
| 输出目标 | 只能到终端 stdout | 可同时到控制台、文件、网络 |
| 开关控制 | 要手动删代码 | 改一个配置就能静默/开启 |
| 格式 | 手动拼字符串 | 自动带时间、级别、来源 |

> 一句话：**`print` 是临时调试用的，`logging` 是给程序长期记录用的。** 上了项目，就该用 logging。

### 日志级别

日志分 5 个级别，从低到高：

| 级别 | 数值 | 含义 | 典型用途 |
|------|------|------|----------|
| `DEBUG` | 10 | 调试信息 | 变量值、执行路径，开发期排查 |
| `INFO` | 20 | 正常运行信息 | "服务已启动"、"用户登录成功" |
| `WARNING` | 30 | 警告，但程序还能跑 | 磁盘快满、用了不推荐写法 |
| `ERROR` | 40 | 错误，某功能失败 | 请求失败、文件打不开 |
| `CRITICAL` | 50 | 致命，程序可能崩溃 | 数据库挂了、内存耗尽 |

> **级别是"门槛"，不是"只显示这一档"**：设置了 `level=INFO`，会显示 `INFO` 及**比它更高**的 `WARNING/ERROR/CRITICAL`，而过滤掉 `DEBUG`。级别越低越啰嗦，越高越关键。

### `basicConfig`：一行起手

最简单的用法，用 `basicConfig` 配置一次，全局生效：

```python
import logging

logging.basicConfig(
    level=logging.INFO,                                   # 只显示 INFO 及以上
    format="%(asctime)s - %(levelname)s - %(message)s"    # 输出格式
)

logging.debug("这是调试信息")     # ❌ 不显示（DEBUG < INFO）
logging.info("服务已启动")        # ✅ 显示
logging.warning("磁盘空间不足")    # ✅ 显示
logging.error("请求失败")          # ✅ 显示
logging.critical("数据库崩溃")     # ✅ 显示
```

```bash
# 输出（格式由 format 控制）：
2026-08-14 10:30:00,123 - INFO - 服务已启动
2026-08-14 10:30:00,125 - WARNING - 磁盘空间不足
...
```

**常用格式占位符**：

| 占位符 | 含义 |
|--------|------|
| `%(asctime)s` | 时间 |
| `%(levelname)s` | 级别名（INFO/ERROR…） |
| `%(message)s` | 日志正文 |
| `%(name)s` | logger 名字（来源模块） |
| `%(filename)s` | 产生日志的文件名 |
| `%(lineno)d` | 行号 |

### logger / handler / formatter：日志三件套

`basicConfig` 是"全家桶一键配置"，但真正工程化的日志要理解三个概念的分工：

```
logger（日志器）── 产生日志的入口，决定"要不要记录这条日志"
   │
   ├── handler（处理器）── 日志发到哪：控制台 / 文件 / 邮件
   │        └── formatter（格式化器）── 日志长什么样
```

- **logger**：你的代码调用 `logger.info(...)` 的那把"钥匙"，靠名字（`__name__`）区分来源；
- **handler**：一个 logger 可以挂多个 handler，同一行日志可以同时写控制台 + 写文件；
- **formatter**：每个 handler 各自绑定格式（控制台简洁，文件详细）。

```python
import logging

# ① 创建 logger
logger = logging.getLogger("myapp")
logger.setLevel(logging.DEBUG)

# ② 创建 handler —— 输出到文件
file_handler = logging.FileHandler("app.log")
file_handler.setLevel(logging.DEBUG)

# ③ 创建 formatter 并绑定到 handler
formatter = logging.Formatter(
    "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
)
file_handler.setFormatter(formatter)

# ④ 把 handler 挂到 logger 上
logger.addHandler(file_handler)

logger.info("这条会写进 app.log 文件")
```

> 一个 logger 挂多个 handler 的典型场景：`StreamHandler` 打到控制台给开发者看，`FileHandler` 落到文件留档给运维查。两者可以挂同一个 logger，也可以各自用不同的 formatter。

### 写日志到文件

除 `FileHandler` 外，工程里最常用的是**滚动文件**——文件大到一定体积就自动切分归档，避免单个日志文件无限膨胀：

```python
import logging
from logging.handlers import RotatingFileHandler

handler = RotatingFileHandler(
    "app.log",
    maxBytes=1024 * 1024,   # 单文件最大 1MB
    backupCount=3           # 最多保留 3 个备份 app.log.1/.2/.3
)
handler.setFormatter(logging.Formatter("%(asctime)s - %(levelname)s - %(message)s"))

logger = logging.getLogger("myapp")
logger.setLevel(logging.INFO)
logger.addHandler(handler)

logger.info("写满 1MB 后，旧的被滚到 app.log.1，新日志继续写 app.log")
```

| handler 类型 | 用途 |
|--------------|------|
| `StreamHandler` | 输出到控制台（stdout/stderr） |
| `FileHandler` | 写入固定文件 |
| `RotatingFileHandler` | 按大小滚动切分 |
| `TimedRotatingFileHandler` | 按时间滚动（每天/每小时一个文件） |

### 多模块日志组织

一个项目有几十个模块，怎么让每个模块的日志都能被统一管理？答案是**每个模块用 `logging.getLogger(__name__)` 拿到自己的 logger**：

```python
# user_service.py
import logging
logger = logging.getLogger(__name__)   # __name__ = "user_service"

def create_user(name):
    logger.info(f"创建用户: {name}")
    ...

# order_service.py
import logging
logger = logging.getLogger(__name__)   # __name__ = "order_service"

def create_order():
    logger.info("创建订单")
    ...
```

> logger 是**按名字形成层级树**的：`a.b` 是 `a` 的子 logger。子 logger 的记录会默认**向上传播**到根 logger。所以在入口（`main.py`）里用一次 `basicConfig` 或给根 logger 配好 handler，所有模块的日志就能统一输出，每个模块自己不用重复配置。

### 日志最佳实践

1. **用 `logging` 而不是 `print`**——print 无法分级、无法落盘、无法一键静默；
2. **每个模块 `getLogger(__name__)`**——日志能追溯到是哪个文件打的；
3. **级别设对**——`INFO` 记录关键节点，`DEBUG` 记录排查细节，别什么都 `print` 或什么都 `error`；
4. **异常要带 `exc_info`**——在 `except` 块里记录完整堆栈，而不是只记一句"出错了"：

```python
try:
    risky_operation()
except Exception:
    logger.exception("操作失败")   # 自动带上完整 traceback
    # 等价于 logger.error("操作失败", exc_info=True)
```

5. **库代码别乱配 `basicConfig`**——库只拿 `getLogger(__name__)` 打日志、不加 handler，把"输出到哪、什么级别"交给使用它的应用去配置。否则你的库会劫持整个程序的日志配置。

### 练习 1：判断输出

下面配置了 `level=logging.WARNING`，写出哪些日志会显示：

```python
import logging
logging.basicConfig(level=logging.WARNING)

logging.debug("A")     # ？
logging.info("B")      # ？
logging.warning("C")   # ？
logging.error("D")     # ？
logging.critical("E")  # ？
```

> [!info]- 答案
> 显示 C、D、E。`WARNING` 是门槛，级别 ≥ WARNING 的（WARNING/ERROR/CRITICAL）都会显示，DEBUG 和 INFO 被过滤。
> ```
> WARNING:root:C
> ERROR:root:D
> CRITICAL:root:E
> ```

### 练习 3：异常日志带堆栈

补全下面代码，让异常发生时日志里包含完整的 traceback：

```python
import logging
logging.basicConfig(level=logging.ERROR)

def divide(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        logging.______("除零错误")   # 填空
```

> [!info]- 答案
> 填 `exception`（或 `error(..., exc_info=True)`）：
> ```python
>     except ZeroDivisionError:
>         logging.exception("除零错误")
> ```
> 输出会带上完整的 traceback，定位到出错的具体行，而不只是 "除零错误" 四个字。

## 🤔 常见误区

1. **误区：「`print` 就够了，专门学 logging 多余」**
   **事实**：脚本阶段 `print` 够用，但项目上线后，你需要日志**分级**（排查时开 DEBUG、平时只记 INFO）、**落盘**（终端关了也能查历史）、**一键静默**（不删代码就能关掉调试输出）。这些 `print` 都做不到。

2. **误区：「设了 `level=INFO` 就只显示 INFO 这一级」**
   **事实**：级别是**门槛**，`INFO` 及以上（WARNING/ERROR/CRITICAL）都会显示，只是过滤掉更低的 DEBUG。想"只看 INFO 不看别的"得用过滤器，非常规需求。

3. **误区：「自定义 logger 和根 logger 互不相干」**
   **事实**：子 logger 的记录会**向上传播**到根 logger。如果你给根 logger 配了 handler，同时又给子 logger 加 handler，同一条日志可能被输出**两次**。通常要么只用根 logger 统一配置，要么设 `logger.propagate = False` 阻断传播。

4. **误区：「`basicConfig` 可以反复调用，随时改配置」**
   **事实**：`basicConfig` 只有**第一次调用生效**（确切说是根 logger 还没有 handler 时才生效）。之后再调是空操作。要动态改配置，得操作 logger/handler 对象本身。

5. **误区：「日志不影响性能，随便打」**
   **事实**：高并发下，大量 DEBUG 日志会显著拖慢程序、撑爆磁盘。所以才有"平时开 INFO、排查才开 DEBUG"的分级策略——用级别控制开销。
