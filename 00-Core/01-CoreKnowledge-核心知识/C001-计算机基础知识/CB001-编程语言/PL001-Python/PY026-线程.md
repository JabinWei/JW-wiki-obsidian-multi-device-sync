## 📚 核心内容

### 什么是线程

线程是操作系统能调度的**最小执行单元**。一个进程可以包含多个线程，它们共享同一块内存空间（全局变量、文件句柄等），但各自有独立的调用栈。

```
进程 A：
├── 线程 1（主线程）  ← 程序入口，默认有一个
├── 线程 2（工作线程） ← 代码创建的
└── 线程 3（工作线程） ← 代码创建的

进程与线程的关键区别：
  进程之间：内存独立，通信靠 IPC（Queue/Pipe/共享内存）
  线程之间：内存共享，通信靠共享变量 + 锁保护
```

|        | 多进程             | 多线程         |
| ------ | --------------- | ----------- |
| 内存     | 独立，不共享          | 共享全局变量      |
| 通信     | IPC（Queue/Pipe） | 共享变量 + Lock |
| 创建开销   | 大（独立内存空间）       | 小（只分配栈）     |
| GIL 影响 | 不受限制（各有各的 GIL）  | 计算密集型无效     |
| 适用     | CPU 密集型         | IO 密集型      |

### 创建线程

`Thread()` 构造函数接受以下参数：

| 参数 | 说明 |
|------|------|
| `target` | 线程执行的函数（必填，没有实际任务的线程没有意义） |
| `args` | 元组，传给 `target` 的位置参数 |
| `kwargs` | 字典，传给 `target` 的关键字参数 |
| `name` | 自定义线程名（默认 `Thread-N`） |
| `daemon` | 布尔值，是否守护线程，必须在 `start()` 前设置 |

```python
import threading
import time

def worker(name, delay):
    print(f'线程 {name} 开始')
    time.sleep(delay)              # sleep 释放 GIL，其他线程可以跑
    print(f'线程 {name} 结束')

# 创建线程
t1 = threading.Thread(target=worker, args=('A', 2))
t2 = threading.Thread(target=worker, kwargs={'name': 'B', 'delay': 1})

t1.start()                         # 启动（非阻塞，主线程继续往下）
t2.start()

t1.join()                          # 等待 t1 结束
t2.join()                          # 等待 t2 结束

print('所有线程已完成')
# 输出顺序：B 结束（delay短）→ A 结束 → 所有线程已完成
```

> `start()` 启动线程后立即返回，主线程不会等它——这就是非阻塞。`join()` 的作用是让主线程停在原地，等子线程跑完再继续往下走。所以 `start()` 和 `join()` 之间写什么，什么就和子线程并发执行。

### 继承式创建（子类化 Thread）

子类化 Thread 本质上就是**重写 `run()` 方法**，把想让线程干的事放进去。框架依然走 `start() → run()` 这条路径，只是 `run()` 里的内容换成了你写的逻辑。

```python
class FetchThread(threading.Thread):
    def __init__(self, url):
        super().__init__()
        self.url = url
        self.result = None

    def run(self):                          # 重写 Thread 的 run()
        print(f'正在请求 {self.url}')
        time.sleep(1)                       # 模拟 IO
        self.result = f'{self.url} 的响应数据'

t = FetchThread('https://api.example.com')
t.start()
t.join()
print(t.result)
```

子类化的价值在于**有状态的线程**：每个线程用实例属性（`self.url`、`self.result`）存储自己的数据，多个线程之间互不干扰——不需要全局变量，也不需要手动把状态传来传去。

**什么时候用子类化？**

| 场景          | 用 `target=函数` 的问题                            | 用子类化的解决                                               |
| ----------- | -------------------------------------------- | ----------------------------------------------------- |
| 线程有自己的返回结果  | 结果散落在全局变量或闭包里，分不清谁的                          | `self.result` 天然隔离，`[t.result for t in threads]` 直接收集 |
| 需要记录重试次数/进度 | 得传一个可变对象进出，还要加锁                              | 每个线程自己的计数器存在实例属性里，线程间不干扰                              |
| 封装可复用的线程组件  | 每次用都要写一遍 `Thread(target=fn, args=...)` 的样板代码 | 一次写好，到处 `MyThread(url).start()`                       |

> 大多数场景用 `target=函数` 就够了。子类化适合线程需要维护自身状态（重试次数、连接对象、执行结果）或需要封装可复用的线程组件时使用。

### daemon 线程

**为什么叫"守护线程"？** 名字来自 Unix 的 daemon 进程——不直接和用户交互，在后台默默提供辅助服务。"守护"不是指守护主线程的安全，而是形容它像后台仆人一样打杂。

**为什么需要 daemon？** 如果一个后台线程是 `while True` 无限循环，默认情况下（`daemon=False`），即使主程序业务逻辑全部跑完，程序也退不出去——因为它会一直等这个后台线程结束。设 `daemon=True` 后，主线程退出时后台线程自动被终止，程序干净退出。

**daemon 与死循环**：后台轮询任务通常是 `while True` + `sleep` 的死循环结构。daemon 不是"让循环停下来"，而是"让程序在循环还跑着的时候也能退出"。主线程退出 → 死循环被强制终止 → 程序干净结束。如果设 `daemon=False`，这个死循环会让程序永远退不出去。

当 `daemon=True` 时，该线程变为**守护线程**——主线程退出时，守护线程自动被杀死，不管它干没干完：

```python
def background_task():
    while True:
        print('心跳...')
        time.sleep(1)

t = threading.Thread(target=background_task, daemon=True)
t.start()
time.sleep(3)
print('主线程退出')   # 守护线程随之结束，不会阻止程序退出
```

| 属性 | 行为 |
|------|------|
| `daemon=False`（默认） | 主线程会等它结束才退出 |
| `daemon=True` | 主线程退出时直接杀掉它 |

> **最佳场景**：后台日志刷新、心跳检测、定时清理——这些任务天然就是 `while True` + `sleep` 的轮询模式，设 daemon 后主程序做完正事随时退出，不用管它们。核心业务线程不要设 daemon——程序退出时可能丢了正在处理的数据。

**daemon 线程退出时会发生什么？**

进程退出时操作系统回收该进程的全部内存，所以**不会有内存泄漏**。但 Python 层面的清理过程不会执行——`finally` 块、`with` 上下文退出、`__del__` 析构函数全部跳过：

| 影响 | 程度 |
|------|------|
| 内存泄漏 | ❌ 不会，OS 全部回收 |
| 文件缓冲区 | ⚠️ 没 flush 的数据丢失（最后几秒的日志/写入） |
| 数据库连接 | ⚠️ 服务端连接等超时回收，频繁退出可能占满连接池 |
| 临时文件 | ⚠️ 没清理的临时文件堆积在磁盘 |

所以 daemon 线程只适合做**丢了也没关系**的事情——日志少几行、心跳停一次都无所谓。必须完成的操作（写文件、操作数据库、释放资源）放在普通线程里。

### CPU 密集型 vs I/O 密集型

理解多线程/多进程的适用场景前，先要分清两类任务：

| | CPU 密集型（CPU-bound） | I/O 密集型（I/O-bound） |
|------|---------|------------|
| 瓶颈 | CPU 算力 | I/O 等待（网络/磁盘/数据库） |
| CPU 状态 | 🔥 一直跑，忙不过来 | 😴 大部分时间空闲在等 |
| 典型场景 | 循环运算、视频编码、科学计算 | 爬虫、文件读写、API 请求 |
| 多线程（Python） | ❌ GIL 串行化，无效 | ✅ I/O 等待时 GIL 释放 |
| 多进程 | ✅ 绕过 GIL，接近 N 倍加速 | ⚠️ 有开销，但也可用 |

**一句话区分**：CPU 密集型 = 程序在**算**（CPU 忙不过来），I/O 密集型 = 程序在**等**（CPU 闲得发慌）。

> 这个区分直接决定你选 `threading` 还是 `multiprocessing`。下面 GIL 小节会解释为什么。

### GIL 与线程

==GIL（Global Interpreter Lock，全局解释器锁）== 是 CPython 解释器中的一个互斥锁。它保证同一时刻**只有一个线程执行 Python 字节码**——即使你有 8 核 CPU，纯 Python 计算任务用多线程也只能用满 1 核。

```python
import threading
import time

def count(n):
    while n > 0:
        n -= 1

# 单线程
start = time.time()
count(100_000_000)
print(f'单线程：{time.time() - start:.2f}s')

# 双线程（计算密集型 — GIL 拖后腿）
start = time.time()
t1 = threading.Thread(target=count, args=(50_000_000,))
t2 = threading.Thread(target=count, args=(50_000_000,))
t1.start(); t2.start()
t1.join(); t2.join()
print(f'双线程：{time.time() - start:.2f}s')   # 不会比单线程快，甚至更慢
```

**GIL 之谜：为什么线程切换了，速度反而更慢？**

上面的例子中，CPU 在 `t1` 和 `t2` 之间反复切换——每次切换都需要保存/恢复线程上下文，切换本身就有开销。但由于 GIL 的存在，**切来切去只有一个人干活，另一个人干瞪眼**——纯属空转。切换开销是额外白费的，总时间 = 两个任务串行计算时间 + N 次上下文切换时间，所以比干脆一个人一口气干完更慢。

| 场景                    | 多线程有用吗 | 原因                    |
| --------------------- | ------ | --------------------- |
| 纯 Python 计算（循环、加减）    | ❌ 没用   | GIL 串行化，线程切换纯浪费       |
| 文件读写、网络请求             | ✅ 有用   | IO 等待时会释放 GIL，让别的线程干活 |
| 调用 C 扩展（numpy、OpenCV） | ✅ 有用   | C 代码可主动释放 GIL         |

> GIL 只在 CPython 中有。Jython（Java 实现）和 IronPython（.NET 实现）没有 GIL。Python 3.13 引入的实验性 free-threaded 模式允许禁用 GIL，但目前生态还不成熟。

### Python 多线程 vs 其他语言

Python（CPython）的多线程和其他语言存在**根本性差异**——不是 API 的差异，而是**执行模型的差异**：

|         | Python（CPython） | Java / C++ / Go / Rust |
| ------- | --------------- | ---------------------- |
| 调度模型    | 多线程**串行**执行字节码  | 多线程**并行**执行            |
| CPU 利用率 | 单核（GIL 限制）      | 多核（1 线程/核）             |
| 计算密集型   | ❌ 多线程无加速，甚至更慢   | ✅ 接近 N 倍加速             |
| IO 密集型  | ✅ IO 等待时释放 GIL  | ✅ 同样受益                 |
| 内存模型    | 共享，GIL 提供伪线程安全  | 共享，需显式同步机制             |

![[90-Storage/98-Asset-资源/InfoGraphic/PY026-线程/Python多线程对比Java-信息图-v1.png]]

**本质区别**：Python 的 GIL 像是「一条车道上的多辆车」——车再多，同一时刻只能有一辆在跑。Java/C++ 的线程像是「多车道高速」——每辆车有自己的车道，真正同时行驶。因此 Python 的计算密集型任务必须用多进程（`multiprocessing`）而不是多线程来加速。

### 竞态条件与 Lock

多个线程同时读写一个共享变量，不保护就会出问题：

```python
import threading

counter = 0

def increment():
    global counter
    for _ in range(100000):
        # counter += 1 不是原子操作
        # 拆开 = 读 counter → 加 1 → 写回 counter
        # 线程可能在「读」之后被切换，另一线程改过 counter
        # 导致写回时覆盖了对方的修改
        temp = counter
        temp = temp + 1
        counter = temp

threads = [threading.Thread(target=increment) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()

print(counter)  # 远小于 400000（每次都不同，竞态条件）
```

==竞态条件（Race Condition）== 就是多个线程并发访问同一数据，最终结果取决于线程调度的时序——这种 bug 难以复现、难以调试。解决方案是加 **Lock**，把读-改-写变成原子操作：

```python
lock = threading.Lock()
counter = 0

def increment():
    global counter
    for _ in range(100000):
        with lock:                   # 同一时刻只有一个线程能进入
            counter += 1

# 4 线程各加 10 万次 → 40 万 ✅
```

**`Lock` vs `RLock`**：

`Lock` 不可重入——同一线程连续 `acquire()` 两次会死锁。`RLock` 可重入——**同一个线程**可以多次获取，配对的 `release()` 全部调用后才释放。注意：可重入不等于多个线程能同时进入，其他线程依然要排队等。

实际场景中，可能出现一个加锁方法调用另一个加锁方法的情况：

```python
# --- Lock：死锁 ---
lock = threading.Lock()

def deposit(amount):
    with lock:                    # 获取锁
        save_balance(get_balance() + amount)

def transfer(amount):
    with lock:                    # 获取锁
        withdraw(amount)          # 内部 with lock → 死锁！
        deposit(amount)           # 内部 with lock → 死锁！
        # ❌ Lock 不认识自己人：同一个线程再来要锁，照样拦

# --- RLock：安全 ---
rlock = threading.RLock()

def deposit(amount):
    with rlock:                   # 同一个线程，计数器 +1，放行
        save_balance(get_balance() + amount)

def transfer(amount):
    with rlock:                   # 获取锁，计数器=1
        withdraw(amount)          # 内部 with rlock → 计数器=2 ✅
        deposit(amount)           # 内部 with rlock → 计数器=3 ✅
    # 退出所有 with，计数器归零，锁释放
```

> **如果能用 Lock 就不要用 RLock**：如果你可以把锁统一放在最外层（`transfer` 里锁一次，`deposit` 和 `withdraw` 内部不加锁），Lock 完全够用，效率更高。RLock 只在「无法避免嵌套加锁」时才有必要。

**哪些场景无法用 Lock 替代？**

| 场景 | 为什么 Lock 不行 |
|------|------|
| 递归函数 | 每层递归都要操作共享数据，第二次递归 `with lock` 就死锁 |
| 回调模式 | A 持锁后调了监听器，监听器回调里又触发了一个加锁方法——A 不知道回调会调谁 |
| 模板方法 | 基类的模板方法加了锁，内部调了子类重写的方法。子类方法单独用也需要锁，但被基类调用时锁已在手 |

```python
# 递归场景：遍历目录树，多线程累计文件大小
rlock = threading.RLock()
total_size = 0

def calc_size(path):
    global total_size
    with rlock:                          # 每层递归都要锁
        total_size += os.path.getsize(path)
    for entry in os.listdir(path):
        sub = os.path.join(path, entry)
        if os.path.isdir(sub):
            calc_size(sub)               # 递归又 with rlock → Lock 死锁
        else:
            with rlock:                  # 同一线程再次获取 → RLock 放行
                total_size += os.path.getsize(sub)
```

> 简单记忆：线性的外层加锁用 `Lock`；出现**同一个线程在不同调用层级都要获取同一把锁**时，用 `RLock`。

> `RLock` 在递归函数、或在 A 方法加锁后内部调用了也加锁的 B 方法时非常有用。简单的临界区保护用 `Lock` 就够。

### 线程安全队列：queue.Queue

`queue` 是 Python 标准库中的一个模块，提供了**线程安全的队列**。队列是一种 FIFO（先进先出）的数据结构——先放进去的数据先被取出来，就像排队一样。

线程间通信的核心场景是**生产者-消费者模式**：一个或多个线程生产数据，一个或多个线程消费数据。最简单的做法是用一个共享 `list`，但需要手动解决三个问题：

| 问题      | 手动 `list` + `Lock`          | `queue.Queue`    |
| ------- | --------------------------- | ---------------- |
| 线程安全    | 每次读写都要手动 `with lock`        | ✅ 内置             |
| 队列空了怎么办 | 轮询 `while not list:` 空转 CPU | ✅ `get()` 自动阻塞等待 |
| 队列满了怎么办 | 自己判断长度，满了要等                 | ✅ `put()` 自动阻塞等待 |

**阻塞等待**的意思是：调用 `get()` 后，如果队列为空，线程就**原地睡着**，不占 CPU。有数据来了，线程自动醒来取走，然后 `get()` 返回。整个过程对调用方来说就是一次普通的函数调用，不需要自己写 `while` 循环反复检查。`put()` 同理——队满则睡，有空间自醒。

多个线程同时阻塞在同一个队列上时，等待顺序是 **FIFO**——先排队等待的线程先被唤醒，不是随机抢，也不是看线程优先级。

手动加锁容易出错——少解锁一次就死锁，锁的范围大了又影响性能。`queue.Queue` 把这些边界条件全部内置了，是最优雅的线程间通信方式：

```python
import threading
import queue
import time

def producer(q):
    for i in range(5):
        time.sleep(0.5)
        q.put(f'任务_{i}')           # 放入队列（线程安全）
    q.put(None)                     # 结束信号

def consumer(q, name):
    while True:
        item = q.get()               # 取出（队列空则阻塞等待）
        if item is None:
            q.put(None)              # 把结束信号放回去，让其他消费者也能收到
            break
        print(f'{name} 处理 {item}')
        q.task_done()                # 标记此任务完成

q = queue.Queue()
threading.Thread(target=producer, args=(q,)).start()
threading.Thread(target=consumer, args=(q, 'Worker-1')).start()
threading.Thread(target=consumer, args=(q, 'Worker-2')).start()
```

`queue.Queue` 常用方法：

| 方法                     | 行为                          |
| ---------------------- | --------------------------- |
| `put(item)`            | 放入（队满则阻塞）                   |
| `put(item, timeout=3)` | 放入，超时抛 `queue.Full`         |
| `get()`                | 取出（队空则阻塞）                   |
| `get(timeout=3)`       | 取出，超时抛 `queue.Empty`        |
| `task_done()`          | 标记一个任务已完成（配合 `join()` 使用）   |
| `q.join()`             | 阻塞直到队列中所有任务都被 `task_done()` |

> 线程间通信的黄金法则：**优先用 `queue.Queue`，不要手动 `Lock` + 共享列表**。Queue 把所有边界条件（空等待、满阻塞、线程安全）都帮你搞定了。

### 控制线程的执行顺序

当线程之间有先后依赖——比如线程 A 必须先写好数据，线程 B 才能读——默认情况下调度器不保证顺序。要明确指定先后，用下面三种机制：

#### Event：显式的「我完成了」信号

```python
from threading import Thread, Event

data = []
done = Event()

def writer():
    data.append('结果')
    done.set()          # 写完，发信号

def reader():
    done.wait()         # 阻塞，直到 writer 调 set()
    print(data[0])      # 保证此时 data 已经写好

Thread(target=reader).start()   # reader 先启动也没关系
Thread(target=writer).start()
# reader 会一直等到 writer 完成后才打印
```

`Event` 建立了一个明确的先后关系：`set()` 之前的操作，一定发生在 `wait()` 返回之后的操作之前。

| 方法 | 作用 |
|------|------|
| `event.set()` | 设置信号（内部标志置 True） |
| `event.wait()` | 阻塞直到信号被设置（可设 timeout） |
| `event.clear()` | 清除信号（标志置 False，可重复使用） |
| `event.is_set()` | 查询当前是否已设置 |

#### Condition：满足某个条件才继续

```python
from threading import Thread, Condition

items = []
cond = Condition()

def producer():
    with cond:
        items.append(1)
        cond.notify()        # 通知：有数据了

def consumer():
    with cond:
        while not items:     # 条件不满足就等
            cond.wait()
        print(items.pop())
```

`Event` 只能表达「一个信号」，`Condition` 可以等任意复杂条件——配合 `wait()`/`notify()`，实现「条件满足才往下走」。

#### queue.Queue：天然的 FIFO 顺序

如果顺序的要求就是「先放入的先处理」，直接放进 `queue.Queue` 即可——队列保证先进先出，处理顺序就是放入顺序（见上一节）。

### ThreadPoolExecutor

每次手动 `Thread(target=fn).start()` 创建一个线程，用完就扔——如果有一万个 URL 要爬，就要创建和销毁一万次线程，开销不小。**线程池**预先创建一批线程，任务来了直接分配，干完回收复用，避免了频繁创建销毁的开销。

`concurrent.futures` 模块提供了 `ThreadPoolExecutor`，通过 `with` 语句管理线程池的生命周期：

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import time
import random

def fetch(url):
    delay = random.uniform(0.5, 2.0)
    time.sleep(delay)
    return f'{url} → {delay:.1f}s'

urls = [f'/api/user/{i}' for i in range(10)]

with ThreadPoolExecutor(max_workers=3) as executor:
    # 方式一：submit + as_completed（不保证顺序，先完成的先处理）
    # Future 做键：as_completed 遍历 key = Future → f.result() 拿结果，future_to_url[f] 反查 URL
    futures = {executor.submit(fetch, url): url for url in urls}
    for f in as_completed(futures):
        print(f.result())

    # 方式二：map（保持顺序，等价于 for url in urls: executor.submit(fetch, url)）
    # for result in executor.map(fetch, urls):
    #     print(result)
```

| 概念 | 说明 |
|------|------|
| `max_workers` | 线程池中最多同时运行的线程数。IO 密集型任务可以设大一些（如 10-50），因为线程大部分时间在等 IO |
| `submit(fn, args...)` | 提交一个任务，立即返回一个 `Future` 对象（不阻塞） |
| `Future` | 一个"未来结果的占位符"——`f.result()` 会阻塞等待这个任务完成并返回结果 |
| `as_completed(futures)` | 遍历已完成的 Future，谁先完成先拿谁（不等顺序） |
| `executor.map(fn, iterable)` | 按 iterable 顺序提交任务，按原顺序返回结果 |
| `with` 退出 | 自动调用 `shutdown(wait=True)`，等待所有线程完成后释放资源 |

> 线程池解决的不是"多线程怎么写"（和手动创建一样），而是"多线程怎么管"——不用自己维护线程列表、不用手动 join 每个线程、不用担心忘记释放资源。

**GIL 下线程池为什么还能用？** GIL 阻止的是**CPU 并发**（多个线程同时执行 Python 字节码），但线程池跑的是 I/O 任务。以 `fetch(url)` 为例——线程发出 HTTP 请求后，在等服务器响应期间，不执行任何 Python 字节码，GIL 自动释放。结果就是 3 个线程**同时在等各自的 I/O 返回**，网络上 3 个请求同时在飞。`max_workers` 控制的是同时等待 I/O 的数量，不是同时执行字节码的数量。

同样的道理，`time.sleep()` 也会释放 GIL——它是**系统调用**，Python 把线程交给 OS 内核由硬件时钟计时，计时期间一行 Python 字节码都不执行。与之对比，`while time.time() - start < 1: pass` 这种忙等是 Python 自己循环检查时间，GIL 一直握着不释放。

### threading.local()

线程间共享全局变量很麻烦（要加锁），但完全不共享又有数据传递问题。`threading.local()` 让每个线程拥有同名但独立的变量副本：

```python
import threading

thread_data = threading.local()

def process():
    # 每个线程独立设置和读取自己的 thread_data.user_id
    thread_data.user_id = threading.current_thread().name
    print(f'{threading.current_thread().name}: user_id = {thread_data.user_id}')

threads = [threading.Thread(target=process) for _ in range(3)]
for t in threads: t.start()
for t in threads: t.join()
# Thread-1: user_id = Thread-1
# Thread-2: user_id = Thread-2
# Thread-3: user_id = Thread-3
```

> 典型的应用场景：Web 框架中每个请求由一个线程处理，用 `threading.local()` 存储当前请求的用户信息、数据库 Session，线程之间不干扰。

### threading 常用方法速查

#### Thread 实例方法

| 方法 | 说明 |
|------|------|
| `Thread(target, args, kwargs)` | 构造线程对象，`target` 为执行函数 |
| `.start()` | 启动线程（每个线程对象只能调用一次） |
| `.join(timeout=None)` | 阻塞等待线程结束，`timeout` 秒后超时返回 |
| `.is_alive()` | 返回 `True` 若线程在运行（`start()` 后、`run()` 结束前） |
| `.name` | 线程名称，可读写（默认 `Thread-N`） |
| `.ident` | 线程 ID，`start()` 后才分配，未启动为 `None` |
| `.native_id` | 操作系统原生线程 ID（全局唯一整数） |
| `.daemon` | 布尔值，是否守护线程，必须在 `start()` 前设置 |

> `ident` 是 Python 内部的线程标识符；`native_id` 是操作系统分配的 TID，可用 `top -H` 或活动监视器查看。

#### threading 模块级函数

| 函数 | 说明 |
|------|------|
| `threading.active_count()` | 当前存活的 `Thread` 对象数量 |
| `threading.current_thread()` | 返回当前执行的 `Thread` 对象 |
| `threading.main_thread()` | 返回主线程对象 |
| `threading.enumerate()` | 返回所有存活线程的 `list` |

#### Lock / RLock 方法

| 方法 | 说明 |
|------|------|
| `lock.acquire(blocking=True)` | 获取锁；`blocking=False` 时立即返回（获取失败返回 `False`） |
| `lock.release()` | 释放锁（未持锁的线程调用会抛 `RuntimeError`） |
| `lock.locked()` | 返回 `True` 若锁当前被持有 |
| `with lock:` | 推荐写法，进入时自动 `acquire()`，退出时自动 `release()` |

#### 其他同步原语

| 类/函数 | 说明 |
|------|------|
| `threading.Timer(interval, function)` | 延迟 `interval` 秒后在新线程中执行 `function`，本质是 `Thread` 子类 |
| `threading.Semaphore(n)` | 信号量，允许最多 `n` 个线程同时访问资源 |
| `threading.Event()` | 线程间简单信号通信——`set()` 发信号，`wait()` 等信号，`clear()` 复位 |
| `threading.Condition()` | 条件变量，配合 `notify()` / `wait()` 实现线程等待特定状态 |

## 🧪 练习 / 验证

## 🤔 常见误区

1. **误区：开了多线程就一定会加速**
   **事实**：计算密集型任务受 GIL 限制，多线程不仅不能加速，线程切换的开销反而让总耗时更长（比单线程还慢）。只有 IO 密集型（网络、文件、sleep）才受益于多线程——IO 等待时 GIL 被释放，其他线程可以跑。

2. **误区：`Lock` 和 `RLock` 通用**
   **事实**：`Lock` 不可重入——同一线程连续 `acquire()` 两次会死锁。递归函数或间接调用自己的方法必须用 `RLock`。

3. **误区：不用 join 也能正常拿到结果**
   **事实**：主线程不 `join()` 就直接打印 `thread.result` 时，工作线程可能还没跑完，拿到的可能是 `None`（不管子线程死活就往下走）。`join()` 确保子线程跑完再继续。

4. **误区：Queue 取了数据后原队列长度就减 1 了**
   **事实**：`get()` 确实移除了数据，队列长度减 1。但 `task_done()` 是独立的计数器——用于 `join()` 判断所有任务是否已处理完，和队列实际大小无关。

5. **误区：用 `list` + `Lock` 也能替代 Queue**
   **事实**：能，但 Queue 内置的条件变量和等待通知机制避免了轮询（while 循环不停检查 list 是否非空），CPU 空转的轮询远不如 Queue 的阻塞等待高效。
